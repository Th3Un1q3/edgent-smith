# Task Delegation Skill

## Mandatory Steps for Delegating Tasks

1. Identify the user request and desired outcome.
2. Look through [Well-Known Workflows](#well-known-workflows) for a ready-made recipe: a match is a row whose File cell names a file that exists and whose Purpose describes this task, and a match is followed by running that workflow's steps. A row whose File cell reads `not implemented` is not a recipe, so that task falls through to step 3.
3. If no workflow exists, decompose the user request into discrete tasks.
4. For each task identify skills that are relevant to the task that are best suited to complete it.
5. Delegate each task with `subtask_run`, providing clear instructions, acceptance criteria, and the context the child needs — its deliverable path, its write allowlist, and the skills to load; independent subtask runs go in one `execute` call, and `subtask_ls` reads status while `subtask_outputs` reads a child's output from that session's stored messages. There is no `task` tool.
6. Track progress against the task list: mark a dispatched task received when its child's report carries the deliverable the dispatch named and the closing sentinel line required by [Report Completeness and Verdict Integrity](#report-completeness-and-verdict-integrity) — a mark of receipt, not a success verdict, which only step 8's fresh verifier issues; an empty or unread report is recovered by reading the child's output with `subtask_outputs` before any status is recorded.
7. Ask the user only in the four cases under [Talking to the User](#talking-to-the-user), each carrying a recommendation.
8. Validate each subagent's work with a session that did not produce it — the closing `PASS` comes from a fresh verifier whose first call runs the gate the criterion names, and step 6's progress check is not that verdict — and iterate until the overall task is completed successfully. Model-level live verification is a delegated CLI/agent run under `.opencode/instructions/live-verification.instructions.md`, never a test file in the unit suite.

## Skill scouting triggers

- Run one `find-skills` pass, or a local skill discovery pass, at the first subtask of every new stage.
- Re-run the pass every 8 dispatches and whenever the task changes domain: evaluation design, conductor workflows, ADRs, harness and agent definitions, testing, docs.
- A pass names 0-3 skills per stage with a reason per skill; zero is valid only after listing the candidate skill names and reading the descriptions of the closest ones.
- Log the pass in the orchestrator's own report to the user — the user-facing message bounded by **Answer first, detail on request** below, not a child's report and not the harness block — naming the skills chosen and rejected, each with its reason.
- When a subtask fails because it lacked a method, scout before retrying it.
- Loading a skill ad hoc by a known name adds that skill to the dispatch without changing the discovery obligation: run and log the stage's pass as well, because a name known in advance answers nothing the pass records.
- **A pass that never reaches a prompt delivered nothing.** The pass is complete when its named skills appear in the next dispatch — the `skills` list or the prompt body. Re-issue that dispatch with the skills attached before the stage continues.

## Report Completeness and Verdict Integrity

These rules bind every prompt the orchestrator writes and every result it accepts.

- **Return the deliverable, never the process.** The first block of a delegated report is the answer the prompt asked for: the ledger, the verdict, the table, or the file path. A task contract, an `execute` block, a plan, or a transcript dump is not a deliverable: the orchestrator re-requests the answer once with the same `task_id` and does not accept the run.
- **A child whose deliverable is an artifact writes it before refining tooling.** Name the path in the prompt's first line and require a first write before tool discovery, because a child that explores first spends its budget and returns the plan in its report instead. A plan that arrives only in a report body is reconstructed into the named path by the orchestrator, and the report is not accepted as the deliverable.
- **Accept the requested set, and nothing else.** Name the affected ids in the acceptance criteria and require the delivered set to equal them: count the ids the change touches before and after, and a member the request did not name fails the criterion even when the request's own goal is met. A producer's coverage for ids "the gateway may add later" is a widening the user never asked for; return it to the caller as a scope question instead of accepting it because the report argues for it.
- **State the return contract in every dispatch, and check both bounds on return.** The agent that delegates names a character cap and an end sentinel in the prompt; on return it checks the body's last line against the sentinel and the body's length against the cap. Pass: the last line is the sentinel and the body stays under the cap. Fail: the body is over the cap or lacks the sentinel — read the tail, narrow the scope, and resume the same child. The sentinel is one final line naming the deliverable, the unit, and the last item's identifier, for example `END ledger — last payments.py:88, unit: statement`, and a word cap compresses prose, never the sentinel. A total is written only when a consumer reads it, and the prompt then names that consumer.
- **Never slice or retype a report.** Pass a child's report whole, or pass a pointer plus the one section the next child needs; a `FACT`/`FINDINGS` block you composed from it is a retype. Render no verdict, ranking, or `PASS`/`FAIL` of your own — the operative rules are **Carry, never retype** and **Judge, never rule** in `.opencode/agents/rug.md`. A character slice removes the tail, where the sentinel and the last rows live; a sliced ledger reads as complete and silently under-feeds the child that receives it. Cap at the render, not at the value: keep the parsed `outputText` whole and slice only the string you print, because a slice written into the call's return expression is the only copy the next step receives, and recovering the discarded span costs a `subtask_outputs` call that returns at most 5 entries.
- **A verdict over 3 or more criteria ships as a file.** Have the child write it to a repository path, return the path and the sentinel, and pass the path on.
- **Never demand verbatim stdout.** A child reports its result (summary plus evidence) and the orchestrator either resumes that `task_id` or dispatches a fresh verifier; raw command output stays in the child's transcript and is retrieved with `subtask_outputs({ task_id })`, which returns that session's stored assistant messages, only when a verifier needs it. If the orchestrator needs a number, it asks the child to report that number with its evidence, or dispatches a verifier; it does not parse a transcript.
- **State the counting granularity.** A statement-by-statement, audit, or enumeration prompt defines the unit before the child starts: sentence, semicolon-joined clause, table row, table row with its header, code-fence delimiter, template field, or tripwire. Two children given no unit return incompatible ledgers that a third child must merge by hand. Name the mandatory fields on that unit — a path, a verdict, a risk tag — and say a row dropping one is a failed row, not a paraphrase: a spec table that leaves them implicit lets a writer drop a required `LOW` tag silently.
- **Recover `status: ok` with empty `outputText` by reading the child's output.** An empty `outputText` on a successful status is an unread result, not a failure: call `subtask_outputs({ task_id })`, which reads the child session's stored assistant messages through the client API so the output survives a plugin restart, and read what it returns. Each entry is returned whole — no per-entry length clamp and no `truncated` flag — so the orchestrator decides how much of a returned `outputText` it keeps, and the tool caps only the entry count: 3 by default, 5 at most, oldest first. An absent, empty, or unknown id returns `[]`, which is unread input rather than a child with no output. A transcript without the answer authorizes a fresh child only on a ground named in [Subagent Failure Recovery](#subagent-failure-recovery). Empty output from every read — `outputText`, `subtask_outputs`, and a resume — is one unread state, and the artifact settles it: read the file body, the identifier count, or the gate output, because a landed edit resumes empty and an interrupted or restarted write leaves a partial set only the tree shows.
- **Resolve numeric contradictions before dispatch.** When a fixed number (`steps: 30`, 24 calls) meets a budget-agnostic rule (a reserve, a per-turn reset) or a config key that must stay, the prompt names which wins and what the number measures. A child given both reads one as a violation of the other and spends its budget reconciling them.
- **Give the child a truncated-input instruction.** Say what it does when its input is incomplete or contradicts the rules: report the defect with the missing span and stop, rather than applying a partial ledger that looks whole.

## Talking to the User

- **Ask once per deliverable, with a recommendation.** The `question` tool is admissible in exactly four cases: (i) a gated action needs authorization (`git add`/`commit`/`push`, a destructive write); (ii) two readings of the deliverable change what gets built and the repo cannot settle which; (iii) an artifact only the user can produce — browser evidence such as address-bar URLs, run logs, screenshots, and DOM snapshots; (iv) a harness-mandated stop — the round cap hit, a criterion that cannot be validated, the same failure repeating twice, or a blocked objective. Cases (i)–(iii) state the recommended default and what would flip the choice; case (iv) states the blocker and the one action that unblocks it. Never ask the user to rank options, choose a format, or grade a report the orchestrator can justify itself — decide, state the decision in one line, and continue. A default that runs when the user stays silent ships with every question. The unit of "once" is the deliverable, not the question or the run: several questions about one deliverable travel merged in a single message, and a second message about that same deliverable in the same run is the consolidated message that was not written. Only the orchestrator asks: `rug-swe` runs with `question: deny`, so a delegated child reports a fork instead of prompting.
- **Answer first, detail on request.** The orchestrator's message opens with the answer in at most 3 lines, carries at most one table, and holds no fenced block that restates a report, ledger, or verdict. Everything past that limit goes to a file the user can open (a repository path) or to an appendix after the answer. A message the user must scroll to reach the outcome fails this rule even when every claim in it is right. The cap governs the user-facing message only: the harness report block its agent definition requires (`Outcome:` / `Request:` / `Changed:` / `Criteria:`, per `.opencode/agents/rug.md`) is appended after the message and does not count against the three lines or the one table.

## Parity and Porting Tasks Require a Surface Inventory

When the request is a parity or porting task — "as close as possible to X", "mirror", "port", "replicate", "match" — decomposition MUST begin with a source→target surface-mapping discovery, never with task breakdown:

- **Inventory first.** Launch a discovery subagent that inventories EVERY element of the source system (plugins, MCP servers, config files, commands, agents, instructions, env vars, tooling) and maps each to a target disposition: IMPLEMENTED / MIGRATE / DROP-WITH-REASON / DEFER.
- **No silent skips.** Every non-implemented element carries a reason; every DEFER/DROP is documented in the target's user-facing docs (README) before the task counts as done. A skip without a documented reason is a failure.
- **Scope questions enumerate.** When a scope-locking question uses a domain word with repo-specific meaning ("plugins", "MCPs", "harness"), the options must list what it concretely includes in THIS repo — inventory first, then ask.
- **Validation checks the mapping.** Give the validation subagent the mapping table; it must verify each row's disposition (implemented actually implemented; migrate actually wired; defer/drop documented), not just the acceptance criteria. This extends asymmetric validation: the validator judges parity-surface completeness, not merely instruction-following.

## What Not to Do

- Delegate tasks without reading the agent cards and sizing the task to the subagent's capabilities.
- Attempt to complete tasks yourself or bypass the RUG orchestrator pattern. All work must be delegated to subagents with explicit scope and acceptance criteria. Where the environment cannot spawn subagents, a human performs the pass.
- Write subagent prompts that instruct bypassing a permission gate or reproducing a denied effect by another mechanism. A prompt names a gated write (`git add`, `git commit`, `git push`) only beside the user's explicit authorization recorded in the current session, because an inferred goal is not authorization; when a delegated action is denied, the subagent reports the exact command, the denial, and the intended outcome, then continues with permitted work — the denial is final for that action and no later prompt asks for a second route to it.
- Sticking to the initial plan despite evidence that it is not working: revise the plan when the evidence shows it failing, and when the same failure repeats twice or a criterion cannot be validated, stop and report the blocker as case (iv) in [Talking to the User](#talking-to-the-user) rather than re-planning again. A TODO list's own ordering is a suggestion, not a scope constraint: when the request says to address the TODOs and the user has accepted breaking changes, the retirement is in scope, and a plan that preserves the legacy path for parity is a re-plan the user has to order.

## Size Bulk Edits to Fit Subagent Budgets

- A single-file edit touching more than ~10 independent blocks (one edit per slide/row across many similar elements) PLUS verification exceeds one subagent's tool-call budget — all edits land, verification is left undone.
- **Split pattern: edits in one part, a fresh verifier in the next.** (a) an implementation subagent does ONLY the edits, given exact old→new strings so it performs no judgment work; (b) a fresh verification subagent that did not produce the edits checks the result, invoked without `task_id` and without `fork_from` and permitted to share the implementer's `execute` call. For more than ~20 blocks, give each part to its own implementation subagent, in parts of at most ~10 blocks each: 24 blocks give three parts, not two of 12.
- Judgment work belongs in a design subagent beforehand — the implementer receives only mechanical edits and no decisions.
- If verification stays with the implementer, plan for a resume: at the budget limit the implementer reports "edits done, verification pending" — resume the same session (`task_id`) to finish verification instead of re-doing edits, because a resume consumes less budget than a relaunch (see [Subagent Failure Recovery](#subagent-failure-recovery)).
- **A slice is a reviewable unit, not a single edit, and one slice is the one deliverable its `subtask_run` receives.** Batch mechanical edits (export trims, constant renames, clamp dedupe, comment-only fixes) into 2-4 slices by default; the ~10-block ceiling above, not the number 4, decides when a batch needs more, so a mechanical batch past ~10 blocks splits further and the two numbers never conflict. Give every behaviour change its own slice whatever the count; do not spend a subagent on every mechanical edit. Every slice ends at a compiling boundary, and a type-level refactor is split from the builder or runtime edit that consumes it, so an interruption leaves a tree that still compiles.
- **Doc sweeps: every occurrence, named list, stated metadata policy.** For a documentation sweep the prompt says every occurrence is in scope and names the files, or the pointer that lists them, plus whether a version, frontmatter, or metadata bump is required by repo policy, so the child does not guess. A per-file line cap collides with a replace-every-occurrence rule: say which one wins, and drop the cap when the sweep must touch every block.
- **Reserve the gate calls in the prompt, named by command.** Reserve explicit calls and name the gate — `just lint` or `just ci-fast` for docs, `validate_memory_frontmatter`, `validate_md_links`, and `audit_fences` for memories — because a child told only a share of its budget spends it on edits and reports the gate as unverified. Name the gate command; never prescribe an implementation command or the order of its steps — the child owns the method. Pair each behavior's test with its implementation in the same pass so RED→GREEN completes inside the budget; an implementer that writes RED tests and stops spends its last calls on gates it never reaches. When test growth would push a test file toward the repo's max-lines cap, give test authoring its own subtask. Capture RED on a stash: copy the pre-change source aside before wiring, so the first gate call observes the failure and a later run still reproduces it; a RED deferred to the last call is lost when the counter or the clock ends the turn.
- **A named gate is not substitutable.** A criterion that names one gate is satisfied only by that gate: schedule the validator's run of it before its first read, in the background, and keep its last two calls for it. A constituent gate in its place fails the criterion. When the changed subsystem has its own instruction file, the dispatcher reads that instruction at discovery and puts its named proof in the brief as a criterion. For example, the instruction for a session state machine names a live agent run as the proof, not only unit tests.
- **Lint after every increment that moves code.** A dedent, extraction, or semaphore removal can push an arrow past complexity 3; run `just lint` when that increment lands, not only in the reserved end-of-run gate, so the fix belongs to the slice that caused it. One lint call per such increment is charged inside the implementation share, and the reserved gate calls still hold the test suite and typecheck; a repetitive content edit takes no per-increment lint.

## Delegation Granularity and Independent Validation

- **One `subtask_run` is one unit of work, not one call.** A single subtask sets one deliverable ("implement file A", never "implement file A and B" or "implement and research"). Several subtask runs belong in the SAME `execute` call when every child reports inside that one call; serializing independent subtasks across separate calls buys no isolation and spends wall-clock and budget. A child whose work outruns that window — a gate run, a full suite, an enumeration past 20 minutes — is dispatched in its own `execute` call as an admitted single-deliverable round: its one child is that round's deliverable, so the two-deliverable rule neither merges nor defers it, and it carries `timeout_minutes` set to its expected wall-clock while the omission default in [Child Budget Accounting](#child-budget-accounting) governs every other child.
- **Independence is per behaviour, not per file.** Two units are independent only when no shared branch, helper, or type surface joins them: an edit-disjoint pair that both read one flag path, or a type-level edit beside the builder that consumes it, is behaviour-coupled, and the batching rule above covers only units that share nothing. Send behaviour-coupled units in separate rounds, and take one read-only tree snapshot (`git status --porcelain`) at each round boundary, because a child's report describes its own session and is stale the moment a sibling holds the same file.
- **Set the goal in the dispatch body.** Call `goal` with `action: "set"` in the same `execute` body as the `subtask_run` calls it covers; a goal set in an earlier body does not cover a later dispatch, and a mid-run rejection costs a rebuilt round.
- **Re-issue a gate-rejected dispatch; do not re-plan it.** The stage is not done until every rejected dispatch has been re-sent unchanged in one body that sets the goal first and dispatches second. A rejected dispatch written off as "handled" is a lost round.
- **A round carries two or more deliverables, or it is a reserve call.** Count the independent deliverables before writing the `execute` block: two or more independent ones go in one round, and a round holding a single step of fewer than 3 tool calls (one output read, one status write, one grep) is merged into the round before it or deferred until a second deliverable exists. The two VERIFY calls, the one DELIVER call, and the admitted single-deliverable round above are the only rounds allowed to stand alone. A run of 5+ rounds before the first answer is a decomposition defect, not diligence.
- **Producers and validators share one call, and independence is no producer identity.** A validator may run in the same `execute` call as its producer; invoke it without `task_id` and without `fork_from` so it judges the tree rather than the producer's transcript. A verifier's fix permission is granted once for the whole declared whitelist — it may fix any file inside that whitelist, and the grant is not renegotiated check by check; choose "report only" for a check where a fix would compound the error (a contested design call, a file outside the whitelist), and never as a condition of independent validation. A report-only verifier that finds a defect costs another author-verify round.
- **Attribute a diff before failing a criterion.** Give the validator the run's expected files and its expected markers alongside the tree, plus the producer's starting tree state — the HEAD rev and the paths already staged or modified before the producer started — so a file outside the run's own set is external by comparison rather than by guess; a staged file, modified file, or `TODO` outside that set came from another actor, so the validator reports it as external and leaves the criterion verdict unchanged. Blaming the run for a concurrent session's staged file costs a rewrite round over damage the run never did. Accept a scope verdict only when the report names the file set it counted, and compare that set with the files the task changed: pass when the named set equals the changed files, and fail, returning the verdict as unread, when it names no set or counts a file already modified before the producer started.
- **The final PASS comes from a non-author.** However the earlier rounds divide authoring and checking, the session that made the last edit does not issue the closing PASS; a fresh session does. A verifier authorized to fix inside a whitelist has authored that edit and cannot close: the closing PASS comes from a different fresh session.
- **The verifier is a fresh subtask that did not produce the artifact, and its first call runs the gate the criterion names.** It reports `UNVERIFIABLE` only after that gate ran, and it quotes each rule verdict from the repository file that states the rule, naming that path, instead of reconstructing the rule from a tool's installed or generated output. The report names the gate command, its result, and one `PASS` or `FAIL` per criterion; a verdict issued before the gate ran is unread and goes back to the caller rather than standing as the closing `PASS`. A refusal is verified at the entry point, not at its lowest helper: when a criterion reads "input X is refused" or "Y is enforced before Z", the verifier's first read after the named gate is the tool or API handler the model calls: follow every helper that handler reaches and report the `file:line` where the check runs. A validation that fires only in a downstream normalizer the handler can bypass, or that contradicts a comment on the handler path, is `FAIL` with the bypass named — not `PASS` because a test reaches the normalizer directly. The dispatch prompt names that entry point, and a verdict that names no entry point is unread.
- **Parse the result before judging it.** A subtask result may arrive as a JSON string; parse it, then read its fields. Confirm the parsed value carries `status` and `outputText` before reading either: an object with neither key is unread, not empty, so spend one `subtask_ls` on the field names and one `subtask_outputs({ task_id })` on the body (it reads the child session's stored messages, so the output survives a plugin restart), never a second `execute` round that re-reads the same absent fields. Never discard a completed result, or redo its work, on a shape assumption — a result that looks failed but was never parsed is unread, not failed: call `subtask_outputs({ task_id })` for the completed output, then resume that `task_id`, and a fresh child is justified only on a ground named in [Subagent Failure Recovery](#subagent-failure-recovery). A producer report truncated by budget exhaustion is not validation and not a PASS; it requires a validator or a resume.

## Prompts Carry Ground Truth, Not Line Numbers

A prompt that names a seam only as "file X line N" spends the subagent's budget re-deriving the real contract, and the surprise lands mid-implementation. Convert discovery into exact facts before writing the prompt:

- **Storage target for every deliverable.** Before dispatch, name where each deliverable lands — a repository path for anything shipped, reviewed, or handed off, or a memory name for knowledge a later reader needs; a deliverable with no named target defaults to the report and the research is never persisted. `.tmp/` is never that target for anything a consumer reads: it holds only an intermediate nobody hands off or the crash-safety checkpoint beside a memory cache, and a set another session acts on is promoted to a repository path or a `mem:` reference before the prompt is written.
- **Exact artifact shape and versions before research.** State the concrete path shape (`group/<name>/` vs `groups/<name>/`) and target installer versions in the prompt; a child that infers the shape returns an unusable layout.
- **Fix the domain vocabulary in the prompt.** List each load-bearing term with its meaning and one disambiguating instance: what each tag value means, and whether "skill name" is the directory (`.agents/skills/<name>/`) or the frontmatter `name`. A term the child must infer from usage spends its discovery calls and still returns a guess.
- **API and type seams.** Name the installed package and version (`@opencode/client 2.0.24`, not a remembered `@opencode-ai/sdk`), the method that actually exists (`catchCause`; Effect v4 has no `catchAll`), and the accepted input shape (`SessionGenerateInput` has no `tools` option). A field that does not exist is a defect the prompt prevents, not one the subagent discovers after writing code against it. A claim about a call signature cites the installed declaration (`.d.ts` or package types) it was read from; when two readers disagree the declaration wins, and neither shape enters a prompt until it has been read.
- **Injection points.** Say where a dependency must be threaded (`context.storage` into `publishInstructionSet`) and which production path always sets a value, so the missing-value case is handled with a stub instead of an invented fallback.
- **Repo ceilings for the files in scope, read from the config at dispatch time.** State the lint and size caps verbatim from the file that enforces them: in this repo `.opencode/eslint.config.js` sets `max-lines` 450 for plugin test files, 350 for non-test plugin sources with `max-depth` 3, and `complexity` 3 uniformly across plugin source and tests, plus `unicorn/prefer-includes`, no-await-expression-member, no-top-level-assignment-in-function. A ceiling recalled from this skill or from memory that contradicts the config is the briefing defect: the child sizes its work to the remembered number and meets the gate afterwards. A subagent that learns a cap from a failing gate refactors or splits files after the work is done, and often runs out of budget first. State the counting rule with the cap: default parameters and optional chains each add a complexity node, and the number that sizes a split is the gate's count over the files in scope, not a count read from the rule text.
- **Exact identifiers.** Feature-flag values (`INSTRUCTION_INJECTION=synthetic`), log-line text including any allowed prefix, which suite a case belongs to, and the gate command with its flags (`just opencode::test --coverage`). Never leave a subagent to invent a name that already exists in the repo. When a prior pass enumerated a live namespace or surface, forward that id list in the prompt: a child told only that the seam is config re-enumerates the namespace and spends its budget on ids the orchestrator already held. Carry each forwarded claim as one JSON object in an array in the prompt body — `[{"id": "<id>", "file": "<path>", "text": "<quoted line>"}]`, never `claims: '<prose>'` — with the quoted line verbatim in `text`, never interpolated inside another string, and each newline escaped as `\n`, because a payload embedded in a template arrives as literal text and the child rebuilds the claims from memory.
- **The request's object, pinned to an enumerated set.** Name in the prompt the exact ids the request covers and state that an id not listed is out of scope. A request naming one capability pins that one id, not its family: a wildcard, glob, or prefix that matches an unlisted id is a widening, whatever the file allows. When the user's words do not name the family, the child has no authority to cover it.
- **Write allowlist.** Name the files the subagent may modify and the files it must not. Enumerate the allowlist from the write sites found in the tree and copy each path from the discovery report that lists it, one path per file the change must touch, so a slice that genuinely needs a new module names that module up front instead of creating a fifth path mid-task; a file the child itself creates or edits outside the allowlist is a scope `FAIL`, while a file the diff shows the child did not write stays external under the attribution rule. User-owned files (`.opencode/agents/rug.md`, `.opencode/agents/rug-swe.md`) stay outside every write scope, however narrow the task. A subagent blocked by a gate inside a narrow task edits a neighbouring file until the gate passes, and the validator finds the damage only after the pass. Name the test mocks of in-scope modules and the type or source files the wiring reaches, say whether updating those mocks is permitted, and grep the changed surface for every test pinning a definition's exact arrays or exact entry list: allowlist each one, or name the ones left out with the red gate each will produce. When a change alters behaviour an existing test asserts, search the changed behaviour's name across the test tree at discovery, because a brief that demands green gates while its allowlist excludes that test is a contradiction the dispatcher resolves before dispatch, not during it. Every path in the write allowlist is opened once before dispatch and copied verbatim from the discovery report, and a path that fails to open is replaced in the same round.
- **Pre-checked edit anchors, written from a re-read.** Quote the exact text each replacement targets and confirm that text exists in the tree before dispatch — an anchor that is paraphrased, or labelled "verbatim" without the check, costs one failed edit per retry until the budget runs out. Open each `path:line` and `path:start-end` in the round it is written, and re-anchor a range whose end falls in a different construct (help text, flag definition, neighbouring function) to the construct actually cited; a citation not re-read in that round is reported as `unverified`, never as the site.
- **Exhaustive means counted, not recalled.** A prompt asking for "every" call site, spawn site, or prompt site in a file names the sweep that enumerates them (`grep -c` of the call name in that file) and requires the count beside the enumerated rows. The validator re-runs the sweep and fails the report when the count differs from the stated one.
- **One winning criterion.** When acceptance criteria conflict — delete a function against forbid touching its file, keep one copy against delete the duplicate — the prompt states which one wins. Turn an unmeasurable bar into a concrete test ("a reader reaching the pointer needs no second lookup"), never an adjective. A prose criterion asks the child to quote the sentence that asserts X in any wording, never to match a literal string: three validators searching different spellings of one clamp ("1-5" against "3 by default, 5 at most") each report FAIL on the same correct text. A subagent left to choose asks and stalls, or satisfies the criterion that damages the tree. A criterion written as a universal (`never`, `must never`) names the existing behaviours it is measured against and says whether the nearest one is an instance or an exception.
- **Operator-supplied values are asked for, never inferred.** When a prompt needs a value only the operator can supply — their email, a token, a domain, an account name — ask for it as the case (iii) artifact in [Talking to the User](#talking-to-the-user) and hold the write: the key stays absent until the answer, with the fill-in named as the one thing the operator must supply, or, when the file must ship before that answer, carries the environment-derived value (`git config`, a sibling env file, a default) marked provisional and never as the authoritative line, because the operator's correction then arrives as a duplicate and the last key wins at load. Before the write is called done, assert the key appears exactly once in the file being written.
- **One child answers at most 3 questions.** Count the answerable questions before dispatch and split above that: a prompt carrying 7 numbered answers plus verbatim quotes overran its 24-call threshold at 26 calls while closing out, so the seventh answer landed after the budget was gone.
- **Name the observable that closes each question, and accept a denial as the answer.** A question with no named observable expands into a two-step hunt that spends the child's budget, and a question whose tool the environment denies was unanswerable as written: every child in one run spent calls confirming a local server that the repo's opencode config forbids `curl` from reaching. Write the closing evidence into the question and say that a denial is an acceptable answer, so the child reports the denial instead of attempting a substitute.
- **Name the authoritative path, and say whether a key must be declared.** A "candidates" list reads as a set of existing paths: a child reported that a candidate list implied configs that do not exist and cost it a call to disprove. Give one path, or one directory plus the pattern that resolves it. Two readings of "required" — schema-level and runtime — made one question unanswerable: state the level at which "required" holds (the installed types reject its absence, or the loader needs it) and which declaration case applies — the key joins an enumerated map the loader walks, or it may stay undeclared like an existing sibling — because the two cases require different prompts and the child cannot infer which one it has.
- **Carry the constraint and ask for the contradiction.** A prompt that states a design decision ("no limit, no modalities") gets compliance and nothing else: the child cannot flag a contradiction in a decision it was handed. State the decision as the requirement and add "if this contradicts the tree, say so in one line", so the report carries the objection the orchestrator needs before it rules. A fork the prompt leaves open — a state that may be absent, a value outside the known set — is closed in the prompt or returned as one report line naming the option taken and the one rejected; a silent choice is a failed prompt, not a judgement call.
- **Scope the verification obligation to the report.** When the prompt asks a child to be careful about verification, say the obligation applies to the child report and not to the document body: a child told only to "mark what is unverified" writes provenance stamps into prose. State each fact you already hold as a constraint on the outcome, with the subagent still owning the method; a fact you do not hold is dispatched to a research subagent that returns it before the implementation prompt is written, never guessed inside that prompt.

## Child Budget Accounting

- **The ~24-call budget is per turn.** A child that idles (every completed subtask does) gets its counter cleared, so a `task_id` resume starts a fresh 24-call window; resume is therefore the cheapest path after idle, not a last resort. Only a child still mid-turn carries its count.
- **24 is the advertised `<task-budget>`, not a hard block.** It triggers a stop-reminder; a child told to stop may overrun, so treat >24 calls as overrun evidence, not a hard limit.
- **Read before you resume.** `subtask_outputs({ task_id })` reads completed output from the child session's stored messages for one orchestrator call and no child budget: read, then resume — the resume resets the budget; a fresh child needs a ground named in [Subagent Failure Recovery](#subagent-failure-recovery).
- **`timeout_minutes` is omitted unless the dispatch's own expected wall-clock exceeds 15 minutes.** Omit it for every other child: the 15-minute default is not a floor, and a habitual, "just in case", or per-dispatch value is a defect. Set it at dispatch, once, to that task's estimated wall-clock only when the task is expected to outrun 15 minutes (a full suite, a CI/gate run, a large enumeration). **Timeout governs wall-clock and is unrelated to the 24-call budget** — a large task does not get more time; it gets a narrower scope or a discovery subtask first. After a child expires, read its latest output with `subtask_outputs`, then resume it; raising the value for the retry is not a remedy.
- **Setup is charged before research.** Skill load, gateway tool discovery, and page discovery consume ~4-6 calls. State the values setup would discover (page id, tab id, tool name, URL pattern, filter syntax) in the prompt, or name the one skill that owns them; never paste one recipe into several prompts, because each child re-derives it and invents its own workaround. A child that reads external sources persists each source to memory as it reads it and returns one `mem:` reference per source; a report without one reference per source is incomplete. Say the split too: ~6 setup, ~12 work, 2 reserved for VERIFY, ~4 report, fields capped at 3-5.
- **Memory writes: pre-name the target and cap discovery.** State the memory name (namespace/path) in the prompt and cap discovery at a few reads; validate only the single written file, not the whole directory. A child that must find the memory name spends its budget on `list_memories` and never writes. Order the subtask write, then the namespace gate, then the read-back, and cap discovery to the calls the prompt already names — the tool signature and the namespace listing it quotes — so the gate is never the last unspent call; a child that spends its calls on discovery or on a second read-back returns a memory it never validated. Write the memory from the finally-approved scope, after the last reversal: a memory written from an intermediate state is rewritten in the same session, never left to contradict the approved change. The prompt also repeats the uniqueness line — "list the namespace, then merge or supersede; one active memory per lesson" — and the child resolves the lesson against the names `list_memories` returns before it writes: a namespace list is a name read, not a body read, so "validate only the single written file" still holds. A namespace index that does not list the namespace's memories is itself a defect the child fixes as a second, separately validated write — that index is its own single file, so repairing it never becomes a whole-directory validation, because an unlisted memory is invisible to the next recall. When the prompt asks for a memory, it says the body carries the lesson about its subject only and that the child's report stays in the report: a body holding report scaffolding — outcome, evidence, residual risk, spend, or provenance of the write — is a failed write the child fixes before it reports. Without that line the child replays its report into the memory.
- **Finalize a decision record once, after the last change.** Decision-record counts — test totals, gate results, mutation scores — are written once after the last change, followed by one read-back; do not rewrite an ADR after every slice, and when a count changes late, update every copy in the same pass.
- **Memory reads cost a call and return the whole body.** One gateway read returns the full memory — an ADR can run to tens of thousands of characters — so an inventory of 20 memories at one read per call exhausts a 24-call budget and truncates the ledger. Batch the reads in one `execute` call with at most 8 memories per gateway call, ask for an index or a per-memory summary when the task does not need every body, and state the batch count only when the inventory exceeds that 8-memory cap, where the batching rule reads it; one line per memory, naming it plus its title or status, is the unit, because a batch above 8 truncates mid-body and the inventory loses its tail.
- **State the evidence bar and the verdict rule.** Define what counts as proof per criterion and what a missing value means (fails the criterion, or passes as "not found"); for a term with two readings, say which wins. Cap each validator at <=3 claims with pages pre-opened: a nine-claim validator dies mid-verification.
- **Cap output length as a reader budget, not a tool limit.** `outputText` and each step's output arrive uncapped: the tool truncates nothing and the result carries no `truncated` flag, so the orchestrator decides how much of a report it keeps, and every extra character spends its own context. A cap is therefore a request the prompt makes and a child can overrun.
- **Ask for one combined character cap that covers every mandatory block.** Ask for one section and a character cap covering the whole delivered text — table, prose, and the reserved sentinel line — for example `<=3500 chars including the table`; a word cap bounds prose only, so a 400-word one-line-per-field ledger still runs past 6000 chars. Every mandatory block — table, required name list, validation block, sentinel — counts inside it. The character cap is gross, measured over that whole text, while the word cap stays net of the blocks, so only prose compresses. Ask the child to measure the per-section counts before its first write and to cut to a per-section target, keeping one call for the final trim: a 4500-char body rewritten five times and still 36 chars over spends the calls its gate needed. For a deliverable with a size or count cap, the child that produces the capped artifact measures the artifact it wrote, in the same step that writes or applies it: a pre-write estimate may size the plan and is never reported as the delivered size, and a report saying "about N characters" fails the criterion.
- **Order sections highest-priority-first, and give the item count only under a character cap.** Give the child the item count next to the cap only when a character cap applies, because the product rule reads it to split the round; with no cap, drop the count. When the prompt mandates several sections, name the one the child may drop, so a child that stops at its cap loses the last section rather than a required one. Width is a second cap: each result row stays one line, and a cell that would wrap becomes a dropped column or a `field=value` pair, because a wide row blows the same character budget.
- **Budget the product: findings × per-finding chars.** 8 findings at 300 chars fit a 3500-char cap and 15 at 400 do not; when the product exceeds the report cap, split the round — findings and risk tags first, evidence in a second round — and read a child report that ends mid-field as the split point to resume from, not a prompt to re-read the child's output. When a dispatch's acceptance criterion demands that content inside one capped artifact, the prompt writer compares the product with the artifact's own declared size limit: pass when it fits, or when the dispatch asks for fewer items or a smaller payload; fail when it exceeds the limit, where no split helps and the items or payload are cut before dispatch.
- **An enumeration read as one set ships as a file, not a split round.** A map or inventory whose rows every consumer needs together — a 33-row implementation map four writers work from — costs more context than one report should carry, and nothing trims it for you now that the tool caps no output. Name the repository path in the prompt, have the child write the full set there and return the path plus the last identifier, and give each consumer the path in place of the body. Splitting by field fits findings a reader judges one at a time; a set split across two rounds drops the rows neither round carried, and `subtask_outputs` returns at most 5 entries, so a set larger than that is read from the file the child wrote, not from the tool.

## Subagent Failure Recovery

Resume is the default continuation, not a last resort. For any follow-up to a child that produced work, pass its `task_id`. A resume carries the child's memory, injected skills, and working state; a relaunch loses them. Launch a fresh child only when the prior context is wrong, the work needs a different specialist, or the result needs fresh judgement. When a fan-out of independent children aborts or is interrupted (`Tool execution interrupted`), retry one child per `execute` call until one completes, then return to the batched shape — the same-call rule in [Delegation Granularity and Independent Validation](#delegation-granularity-and-independent-validation) still governs first dispatch.

When a subagent returns no usable output or exhausts its budget without producing code:

1. **List, read the output, then resume.** Take the identifier from a `subtask_ls` call made in the same turn, never from memory or an earlier turn. Call `subtask_outputs({ task_id })` first (one orchestrator call, no child budget) to collect output even if the resume fails, then re-invoke the subagent with the listed `task_id` and a prompt like "report what you did and what remains." `subtask_ls` returns one entry per child carrying its `task_id` and status, so the listing is the only source that shows the id is live. Pass: the resume call's identifier appears in that turn's `subtask_ls` output. Fail: the resume returns an error or unknown-identifier result, or the identifier reaches the call with no `subtask_ls` output earlier in the turn. Context reuse is cheaper than re-discovery, and the resume resets the budget: an idled child gets a fresh 24-call window. If the resumed subagent still produces nothing, proceed to step 2.
2. **Relaunch with narrow scope once a resume yields nothing usable — the third ground, a result needing fresh judgement.** Launch a fresh subagent with a single deliverable, the task's steps (not command recipes), and an explicit directive to produce output immediately. Broad prompts ("implement X, Y, and Z") cause budget exhaustion on discovery.

## Pilot-first rule for research campaigns

- Any research campaign spanning >5 entities MUST start with a single-entity pilot: capture one entity end-to-end (search → open → extract → store in memory → report), confirm the pipeline, then proceed.
- Then run batches of ≤5 entities, with per-item recovery: on batch failure, save what succeeded (memory store first), retry ONLY the failed items — once — with a changed approach (smaller batch, different extractor, different navigation, longer waits). NEVER retry the same failing batch repeatedly.
- Resume by `task_id` for resumable research scopes under the rule in [Subagent Failure Recovery](#subagent-failure-recovery): resumption preserves calibrated technique and saves re-deriving context.
- Store results per-entity in memory as the primary cache; a checkpoint file is a secondary crash-safety copy. Cap what that cache accumulates: one case per failure group, not per failure, and a retrospective that would write more than three cases merges the smallest into its nearest group instead of adding a fourth.
