# Task Delegation Skill

Teaches the RUG (Repeat Until Good) orchestrator pattern for decomposing user requests into discrete, independently-completable agent subagent tasks and routing them to specialized agents based on scope, expertise, and limitations.

## Mandatory Steps for Delegating Tasks

1. Identify the user request and desired outcome.
2. Look through the list of workflows to see if there is a ready-made recipe for the task in [Well-Known Workflows](#well-known-workflows). If so, follow the workflow steps.
3. If no workflow exists, decompose the user request into discrete tasks.
4. For each task identify skills that are relevant to the task that are best suited to complete it.
5. Delegate each task with `subtask_run`, providing clear instructions, acceptance criteria, and any necessary context; independent subtask runs go in one `execute` call, and `subtask_ls`/`subtask_tail` read status and output. There is no `task` tool.
6. Track progress against the task list and confirm that each subagent completes its task successfully.
7. Ask the user only in the four cases under [Talking to the User](#talking-to-the-user), each carrying a recommendation.
8. Validate the results of each subagent's work independently, and iterate until the overall task is completed successfully. Model-level live verification follows `.opencode/instructions/live-verification.instructions.md`.

## Skill scouting triggers

- Run one `find-skills` pass, or a local skill discovery pass, at the first subtask of EVERY new stage, not only the first stage.
- Re-run the pass every 8 dispatches and whenever the task changes domain: evaluation design, conductor workflows, ADRs, harness and agent definitions, testing, docs.
- A pass names 0-3 skills per stage with a reason per skill; zero is valid only after listing the candidate skill names and reading the descriptions of the closest ones.
- Log the pass in the report: the skills chosen and rejected, each with its reason.
- When a subtask fails because it lacked a method, scout before retrying it.
- Loading a skill ad hoc by a known name is not a substitute for discovery.

## Report Completeness and Verdict Integrity

These rules bind every prompt the orchestrator writes and every result it accepts.

- **Return the deliverable, never the process.** The first block of a delegated report is the answer the prompt asked for: the ledger, the verdict, the table, or the file path. A task contract, an `execute` block, a plan, or a transcript dump is not a deliverable: the orchestrator re-requests the answer once with the same `task_id` and does not accept the run.
- **Close every report with a sentinel that names the unit and its last identifier.** A delegated report, ledger, or enumeration ends with one final line naming the deliverable, the unit, and the last item's identifier, for example `END ledger — last payments.py:88, unit: statement`. A report without that line is truncated, never complete: the orchestrator reports the missing tail and re-requests the remainder rather than passing the body downstream. A word cap compresses prose, never the sentinel. A total is written only when a consumer reads it, and the prompt then names that consumer.
- **Never slice or retype a report.** Pass a child's report whole, or pass a pointer plus the one section the next child needs; a `FACT`/`FINDINGS` block you composed from it is a retype. Render no verdict, ranking, or `PASS`/`FAIL` of your own — the operative rules are **Carry, never retype** and **Judge, never rule** in `.opencode/agents/rug.md`. A character slice removes the tail, where the sentinel and the last rows live; a sliced ledger reads as complete and silently under-feeds the child that receives it.
- **State the counting granularity.** A statement-by-statement, audit, or enumeration prompt defines the unit before the child starts: sentence, semicolon-joined clause, table row, table row with its header, code-fence delimiter, template field, or tripwire. Two children given no unit return incompatible ledgers that a third child must merge by hand. Name the mandatory fields on that unit — a path, a verdict, a risk tag — and say a row dropping one is a failed row, not a paraphrase: a spec table that leaves them implicit lets a writer drop a required `LOW` tag silently.
- **Recover `status: ok` with empty `outputText` by tailing.** An empty `outputText` on a successful status is an unread result, not a failure: call `subtask_tail({ task_id })` and read the transcript. A transcript without the answer authorizes a fresh child only on a ground named in [Subagent Failure Recovery](#subagent-failure-recovery).
- **Resolve numeric contradictions before dispatch.** When a fixed number (`steps: 30`, 24 calls) meets a budget-agnostic rule (a reserve, a per-turn reset) or a config key that must stay, the prompt names which wins and what the number measures. A child given both reads one as a violation of the other and spends its budget reconciling them.
- **Give the child a truncated-input instruction.** Say what it does when its input is incomplete or contradicts the rules: report the defect with the missing span and stop, rather than applying a partial ledger that looks whole.

## Talking to the User

- **Ask once, with a recommendation.** The `question` tool is admissible in exactly four cases: (i) a gated action needs authorization (`git add`/`commit`/`push`, a destructive write); (ii) two readings of the deliverable change what gets built and the repo cannot settle which; (iii) an artifact only the user can produce — browser evidence such as address-bar URLs, run logs, screenshots, and DOM snapshots; (iv) a harness-mandated stop — the round cap hit, a criterion that cannot be validated, the same failure repeating twice, or a blocked objective. Cases (i)–(iii) state the recommended default and what would flip the choice; case (iv) states the blocker and the one action that unblocks it. Never ask the user to rank options, choose a format, or grade a report the orchestrator can justify itself — decide, state the decision in one line, and continue. A default that runs when the user stays silent ships with every question, and two questions about the same deliverable in one run are one consolidated message that was not written. Only the orchestrator asks: `rug-swe` runs with `question: deny`, so a delegated child reports a fork instead of prompting.
- **Answer first, detail on request.** The orchestrator's message opens with the answer in at most 3 lines, carries at most one table, and holds no fenced block that restates a report, ledger, or verdict. Everything past that limit goes to a file the user can open (a repository path or `.tmp/`) or to an appendix after the answer. A message the user must scroll to reach the outcome fails this rule even when every claim in it is right. The cap governs the user-facing message only: the harness report block its agent definition requires (`Outcome:` / `Request:` / `Changed:` / `Criteria:`, per `.opencode/agents/rug.md`) is appended after the message and does not count against the three lines or the one table.

## Parity and Porting Tasks Require a Surface Inventory

When the request is a parity or porting task — "as close as possible to X", "mirror", "port", "replicate", "match" — decomposition MUST begin with a source→target surface-mapping discovery, never with task breakdown:

- **Inventory first.** Launch a discovery subagent that inventories EVERY element of the source system (plugins, MCP servers, config files, commands, agents, instructions, env vars, tooling) and maps each to a target disposition: IMPLEMENTED / MIGRATE / DROP-WITH-REASON / DEFER.
- **No silent skips.** Every non-implemented element carries a reason; every DEFER/DROP is documented in the target's user-facing docs (README) before the task counts as done. A skip without a documented reason is a failure.
- **Scope questions enumerate.** When a scope-locking question uses a domain word with repo-specific meaning ("plugins", "MCPs", "harness"), the options must list what it concretely includes in THIS repo — inventory first, then ask.
- **Validation checks the mapping.** Give the validation subagent the mapping table; it must verify each row's disposition (implemented actually implemented; migrate actually wired; defer/drop documented), not just the acceptance criteria. This extends asymmetric validation: the validator judges parity-surface completeness, not merely instruction-following.

## What Not to Do

- Delegate tasks without reading the agent cards and rightsizing the task to the subagent's capabilities.
- Attempt to complete tasks yourself or bypass the RUG orchestrator pattern. All work must be delegated to subagents with explicit scope and acceptance criteria. Where the environment cannot spawn subagents, a human performs the pass.
- Write subagent prompts that instruct bypassing a permission gate or reproducing a denied effect by another mechanism. Gated writes (`git add`, `git commit`, `git push`) require explicit user authorization in the current session; when a delegated action is denied, the subagent reports the exact command, the denial, and the intended outcome, then continues with permitted work — the denial is final for that action.
- Sticking to the initial plan despite evidence that it is not working. Be flexible and willing to adjust the plan as needed based on feedback and results.

## Size Bulk Edits to Fit Subagent Budgets

- A single-file edit touching more than ~10 independent blocks (one edit per slide/row across many similar elements) PLUS verification exceeds one subagent's tool-call budget — all edits land, verification is left undone.
- Split pattern: (a) an implementation subagent does ONLY the edits, given exact old→new strings so it performs no judgment work; (b) a fresh verification subagent that did not produce the edits checks the result, invoked without `task_id` and without `fork_from` and permitted to share the implementer's `execute` call.
- For more than ~20 blocks, split the edits into halves and give each half to its own implementation subagent.
- Judgment work belongs in a design subagent beforehand — the implementer receives only mechanical edits and no decisions.
- If verification stays with the implementer, plan for a resume: at the budget limit the implementer reports "edits done, verification pending" — resume the same session (`task_id`) to finish verification instead of re-doing edits.
- A resume consumes less budget than a relaunch: context reuse beats re-discovery (see Subagent Failure Recovery).
- **Doc sweeps: every occurrence, named list, stated metadata policy.** For a documentation sweep the prompt says every occurrence is in scope and names the files, or the pointer that lists them, plus whether a version, frontmatter, or metadata bump is required by repo policy, so the child does not guess. A per-file line cap collides with a replace-every-occurrence rule: say which one wins, and drop the cap when the sweep must touch every block.
- **Reserve the gate calls in the prompt.** State the split: ~70% implementation and tests, ~20% gates, ~10% reporting. Pair each behavior's test with its implementation in the same pass so RED→GREEN completes inside the budget; an implementer that writes RED tests and stops spends its last calls on gates it never reaches. When test growth would push a test file toward the repo's max-lines cap, give test authoring its own subtask.
- **Name the reserved gates, not a percentage.** A percentage buys nothing: reserve explicit calls and name the command — `just lint` or `just ci-fast` for docs, `validate_memory_frontmatter`, `validate_md_links`, and `audit_fences` for memories. A child told only "~20% gates" spends the budget on edits and reports the gate as unverified. Name the gate command; never prescribe an implementation command or the order of its steps — the child owns the method.

## Delegation Granularity and Independent Validation

- **One `subtask_run` is one unit of work, not one call.** A single subtask sets one deliverable ("implement file A", never "implement file A and B" or "implement and research"). Several subtask runs belong in the SAME `execute` call; serializing independent subtasks across separate calls buys no isolation and spends wall-clock and budget.
- **A round carries two or more deliverables, or it is a reserve call.** Count the independent deliverables before writing the `execute` block: two or more independent ones go in one round, and a round holding a single step of fewer than 3 tool calls (one re-tail, one status write, one grep) is merged into the round before it or deferred until a second deliverable exists. The two VERIFY calls and the one DELIVER call are the only rounds allowed to stand alone. A run of 5+ rounds before the first answer is a decomposition defect, not diligence.
- **Producers and validators share one call.** A validator may run in the same `execute` call as its producer; invoke it without `task_id` and without `fork_from` so it judges the tree rather than the producer's transcript.
- **Independence is no producer identity, not no write access.** A verifier may be authorized to fix inside a declared whitelist; "report only" is a choice for checks where a fix would compound the error (a contested design call, a file outside the whitelist), never a requirement of independent validation. A report-only verifier that finds a defect costs another author-verify round.
- **The final PASS comes from a non-author.** However the earlier rounds divide authoring and checking, the session that made the last edit does not issue the closing PASS; a fresh session does. A verifier authorized to fix inside a whitelist has authored that edit and cannot close: the closing PASS comes from a different fresh session.
- **Parse the result before judging it.** A subtask result may arrive as a JSON string; parse it, then read its fields. Never discard a completed result, or redo its work, on a shape assumption. A producer report truncated by budget exhaustion is not validation and not a PASS; it requires a validator or a resume.
- **A shape assumption is never grounds to relaunch.** A result that looks failed but was never parsed is unread, not failed: call `subtask_tail({ task_id })` for the completed output, then resume that `task_id`. A fresh child is justified only on a ground named in [Subagent Failure Recovery](#subagent-failure-recovery).

## Prompts Carry Ground Truth, Not Line Numbers

A prompt that names a seam only as "file X line N" spends the subagent's budget re-deriving the real contract, and the surprise lands mid-implementation. Convert discovery into exact facts before writing the prompt:

- **Storage target for every deliverable.** Before dispatch, name where each deliverable lands — repository path, memory name, or `.tmp/` path. A deliverable with no named target defaults to the report and the research is never persisted.
- **Exact artifact shape and versions before research.** State the concrete path shape (`group/<name>/` vs `groups/<name>/`) and target installer versions in the prompt; a child that infers the shape returns an unusable layout.
- **Fix the domain vocabulary in the prompt.** List each load-bearing term with its meaning and one disambiguating instance: what each tag value means, and whether "skill name" is the directory (`.agents/skills/<name>/`) or the frontmatter `name`. A term the child must infer from usage spends its discovery calls and still returns a guess.
- **API and type seams.** Name the installed package and version (`@opencode/client 2.0.24`, not a remembered `@opencode-ai/sdk`), the method that actually exists (`catchCause`; Effect v4 has no `catchAll`), and the accepted input shape (`SessionGenerateInput` has no `tools` option). A field that does not exist is a defect the prompt prevents, not one the subagent discovers after writing code against it.
- **Injection points.** Say where a dependency must be threaded (`context.storage` into `publishInstructionSet`) and which production path always sets a value, so the missing-value case is handled with a stub instead of an invented fallback.
- **Repo ceilings for the files in scope.** State the lint and size caps verbatim: max-lines 650 per test file, complexity 8, `unicorn/prefer-includes`, no-await-expression-member, no-top-level-assignment-in-function. A subagent that learns a cap from a failing gate refactors or splits files after the work is done, and often runs out of budget first.
- **Exact identifiers.** Feature-flag values (`INSTRUCTION_INJECTION=synthetic`), log-line text including any allowed prefix, which suite a case belongs to, and the gate command with its flags (`just opencode::test --coverage`). Never leave a subagent to invent a name that already exists in the repo.
- **Write allowlist.** Name the files the subagent may modify and the files it must not. User-owned files (`.opencode/agents/rug.md`, `.opencode/agents/rug-swe.md`) stay outside every write scope, however narrow the task. A subagent blocked by a gate inside a narrow task edits a neighbouring file until the gate passes, and the validator finds the damage only after the pass.
- **Pre-checked edit anchors.** Quote the exact text each replacement targets and confirm that text exists in the tree before dispatch. An anchor that is paraphrased, or labelled "verbatim" without the check, costs one failed edit per retry until the budget runs out.
- **One winning criterion.** When acceptance criteria conflict — delete a function against forbid touching its file, keep one copy against delete the duplicate — the prompt states which one wins. Turn an unmeasurable bar into a concrete test ("a reader reaching the pointer needs no second lookup"), never an adjective. A subagent left to choose asks and stalls, or satisfies the criterion that damages the tree.
- **Scope the verification obligation to the report.** When the prompt asks a child to be careful about verification, say the obligation applies to the child report and not to the document body: a child told only to "mark what is unverified" writes provenance stamps into prose.
  State each fact as a constraint on the outcome; the subagent still owns the method. Facts the orchestrator does not have yet belong in a research subagent that returns them, not in a guess inside the implementation prompt.

## Child Budget Accounting
- **The ~24-call budget is per turn.** A child that idles (every completed subtask does) gets its counter cleared, so a `task_id` resume starts a fresh 24-call window; resume is therefore the cheapest path after idle, not a last resort. Only a child still mid-turn carries its count. 24 is the advertised `<task-budget>` and triggers a stop-reminder, not a hard block; a child told to stop may overrun, so treat >24 calls as overrun evidence, not a hard limit. `subtask_tail({ task_id })` reads completed output for one orchestrator call and no child budget: tail, then resume — the resume resets the budget; a fresh child needs a ground named in [Subagent Failure Recovery](#subagent-failure-recovery).
- **Setup is charged before research.** Skill load, gateway tool discovery, and page discovery consume ~4-6 calls. State the values setup would discover (page id, tab id, tool name, URL pattern, filter syntax) in the prompt, or name the one skill that owns them; never paste one recipe into several prompts, because each child re-derives it and invents its own workaround. Say the split too: ~6 setup, ~12 work, 2 reserved for VERIFY, ~4 report, fields capped at 3-5.
- **Memory writes: pre-name the target and cap discovery.** State the memory name (namespace/path) in the prompt and cap discovery at a few reads; validate only the single written file, not the whole directory. A child that must find the memory name spends its budget on `list_memories` and never writes.
- **Memory reads cost a call and return the whole body.** One gateway read returns the full memory — an ADR can run to tens of thousands of characters — so an inventory of 20 memories at one read per call exhausts a 24-call budget and truncates the ledger. Batch the reads in one `execute` call with at most 8 memories per gateway call, ask for an index or a per-memory summary when the task does not need every body, and state the batch count only when the inventory exceeds that 8-memory cap, where the batching rule reads it; one line per memory, naming it plus its title or status, is the unit, because a batch above 8 truncates mid-body and the inventory loses its tail.
- **State the evidence bar and the verdict rule.** Define what counts as proof per criterion and what a missing value means (fails the criterion, or passes as "not found"); for a term with two readings, say which wins. Cap each validator at <=3 claims with pages pre-opened: a nine-claim validator dies mid-verification.
- **Cap output length against the mandatory content.** `outputText` holds ~4000 chars, so ask for one section and a character cap covering the whole delivered text — table, prose, and the reserved sentinel line — for example `<=3500 chars including the table`; a word cap bounds prose only, so a 400-word one-line-per-field ledger still runs past 6000 chars and truncates silently. Give one combined budget and say that every mandatory block — table, required name list, validation block, sentinel — counts inside it. When both caps apply, the character cap is gross — measured over the whole delivered text including the blocks and the sentinel — while the word cap stays net of the blocks, so only prose compresses: a 450-word cap with no gross character budget truncates the delivery. Give the child the item count next to the cap only when a character cap applies, because the product rule reads it to split the round; with no cap, drop the count. When the prompt mandates several sections, order them highest-priority-first, so a cut at the 4000-char cap drops the last section rather than a required one. Width is a second cap: each result row stays one line, and a cell that would wrap becomes a dropped column or a `field=value` pair, because a wide row truncates mid-cell even when the character count fits. Budget the product: findings × per-finding chars, so 8 findings at 300 chars fit a 3500-char cap and 15 at 400 do not; when the product exceeds the cap, split the round — findings and risk tags first, evidence in a second round — and treat a tail that returns text cut at the cap as truncation to resume with that split, not another tail.

## Subagent Failure Recovery

Resume is the default continuation, not a last resort. For any follow-up to a child that produced work, pass its `task_id`. A resume carries the child's memory, injected skills, and working state; a relaunch loses them. Launch a fresh child only when the prior context is wrong, the work needs a different specialist, or the result needs fresh judgement.

When a subagent returns no usable output or exhausts its budget without producing code:

1. **Tail, then resume.** Re-invoke the subagent with the same `task_id` and a prompt like "report what you did and what remains." Context reuse is cheaper than re-discovery, and the resume resets the budget: an idled child gets a fresh 24-call window. Call `subtask_tail({ task_id })` first (one orchestrator call, no child budget) to collect output even if the resume fails. If the resumed subagent still produces nothing, proceed to step 2.
2. **Relaunch with narrow scope once a resume yields nothing usable — the third ground, a result needing fresh judgement.** Launch a fresh subagent with a single deliverable, the task's steps (not command recipes), and an explicit directive to produce output immediately. Broad prompts ("implement X, Y, and Z") cause budget exhaustion on discovery — scope each subagent to one deliverable.

## Pilot-first rule for research campaigns

- Any research campaign spanning >5 entities MUST start with a single-entity pilot: capture one entity end-to-end (search → open → extract → store in memory → report), confirm the pipeline, then proceed.
- Then run batches of ≤5 entities, with per-item recovery: on batch failure, save what succeeded (memory store first), retry ONLY the failed items — once — with a changed approach (smaller batch, different extractor, different navigation, longer waits). NEVER retry the same failing batch repeatedly.
- Resume by `task_id` for resumable research scopes under the rule in [Subagent Failure Recovery](#subagent-failure-recovery): resumption preserves calibrated technique and saves re-deriving context.
- Store results per-entity in memory as the primary cache; a checkpoint file is a secondary crash-safety copy.
