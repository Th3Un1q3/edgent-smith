# ADR Rules

Conventions for writing and maintaining Architecture Decision Records (domain: `mem:architecture/about`; skeleton: `mem:architecture/adr-template`).

- Write an ADR when a non-trivial architecture/design decision has ≥2 viable options with trade-offs (one ADR per decision).
- Ids are sequential integers (ADR-001, ADR-002, ...); the memory slug follows the id (`ADR-001-<kebab-slug>`).
- ADRs live under the `architecture/adr/` subnamespace, one memory per ADR, named `ADR-NNN-<kebab-slug>`.
- Frontmatter fields are REQUIRED: id, title, status, date, scope.
- Population order: fill an ADR in five stages — `## Criteria` → `## Options considered` → `## Non-negotiable requirements` → `## Scoring` → `## Decision`. An optional `## Context` problem statement may precede `## Criteria`; `## Consequences` follows `## Decision`. `## Decision` comes LAST because it is the output of criteria + options + non-negotiables + scoring, not an entry point.
- Criteria are derived per decision, 3 to 5 of them, chosen for THIS decision's dominant risk; there is no mandatory universal set. Reuse Maintainability/Flexibility/Implementation ease/Initial implementation cost only when they discriminate for this decision. For each chosen criterion state why it belongs to this decision's kind (a decision that widens the attack surface scores security of exposure; a decision an operator must run repeatedly scores familiarity/operational load). Record in the ADR why the chosen set fits and which criteria a reader might expect but that were rejected as non-discriminating for this decision.
- Scoring: score every eligible option on every criterion on the -2..+2 scale and state explicit totals; scores stay unweighted unless the ADR states and justifies weights.
- Non-negotiable requirements are hard, testable filters, distinct from criteria: state each so a reader can mark an option pass or fail, and derive them from the actual constraint set (user constraints, security floor, existing repo invariants), never invented to fit a favourite option. An option failing any requirement is ineligible: record it, name the requirement it violates, say it was filtered out, and do not score it into the totals. If filtering leaves a single eligible option, say so plainly instead of manufacturing a close contest; criteria discriminate only among eligible options.
- Grandfathering: ADRs already written in the old order are grandfathered — never rewrite history. The population order and criterion method apply to ADRs authored, or still `draft`/`proposed`, from now on, and an ADR being reworked while still proposed may adopt the new shape in place.
- Status lifecycle: `draft` → `proposed` → `accepted` or `rejected`; a later decision that changes an earlier one makes the earlier `superseded` (add a `superseded-by: ADR-NNN` note to its frontmatter) — NEVER rewrite history.
- Score discipline: the highest total among eligible options wins; constraints (e.g., operator requirements) may override scores but MUST be documented in the ADR, not in the Decision, which stays self-contained.
- Options considered: at least 2, each with pros AND cons.
- Keep ADRs lightweight (≈1 memory, concise bullets); link evidence (research memories, files) via `mem:` refs.
- Reference `mem:architecture/adr-template` and `mem:architecture/adr-rules` when writing a new ADR.
- Decision style: the `## Decision` must be a clear, self-containing statement of what was decided (readable standalone). Form it as "<what is decided> <chosen approach>" plus the essential implementation detail, in declarative voice — e.g., "One-time envelope implemented as an XML tag and parsed with a regex." Do NOT recap scores, list rejected options, or hedge ("probably", "better", "close"); the rationale (criteria, options, non-negotiable requirements, scoring) belongs in the stages above it.
