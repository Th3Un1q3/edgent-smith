# ADR-011 migration plan: native session-scoped instruction entries

Status: proposed
Date: 2026-10-21
Scope: planning artifact only. The migration is not implemented by this document.

## 1. Summary

ADR-011 retires the synthetic user-turn carrier in `.opencode/plugins/instructions-loader.ts` and moves instruction guidance onto the opencode v2 session-scoped instruction entry API, one keyed JSON value per session, rendered by the runtime as a `<context key="...">` block at the end of the instruction sequence. The carrier already exists in this repository as `.opencode/plugins/helpers/instruction-entry-client.ts` and is used by `.opencode/plugins/workflow.ts:141`; the loader is the call site that still writes through `context.session.prompt` (`:114`), a storage stash (`:115`), and an `event.system` push (`:127`). The migration has six phases: build the carrier primitives, add a flag-gated native publication path to the loader while the synthetic path stays the default, retire the dead `idempotencyKey` field the native path no longer needs, add the unit, live and regression test suites, flip the default to `native` behind `INSTRUCTION_INJECTION` after the live measurements, and finally migrate the `<task_skills>` call site and delete the synthetic branch together with its bookkeeping. Selection (`.opencode/instructions/*.instructions.md`, 18 files), gating (`TARGETED_TOOLS` applied after `readFilePath`), and the `buildSteeringMessage` payload stay byte-identical throughout. All 103 extracted ADR requirements are mapped in section 4 and traced to their satisfying phase in section 10.

### 2.2 What ADR-011 mandates

ADR-011 is stored at `mem:architecture/adr/ADR-011-native-session-scoped-instruction-entries`. Its normative surface:

- Client methods `client.session.instructions.entry.put({ sessionID, key, value })`, `remove({ sessionID, key })`, `list({ sessionID })`.
- HTTP routes `GET /api/experimental/session/:sessionID/instructions/entries`, `PUT /api/experimental/session/:sessionID/instructions/entries/:key` with body `{ value }`, `DELETE /api/experimental/session/:sessionID/instructions/entries/:key`. There is no get-by-key route; read-back is list-and-filter.
- Rendering `<context key="<key>">` plus `renderValue(value)` plus `</context>`, where a string value renders verbatim and any other value renders as `JSON.stringify(value, null, 2)`. Changes and removals carry runtime narration.
- Keys matching `^[a-z0-9][a-z0-9._-]*$`, namespaced by the server as `api/<key>`. Values capped at `MaxValueBytes = 256 KiB`, measured as `Buffer.byteLength(JSON.stringify(value), "utf8")`.
- A harness-side helper module `.opencode/plugins/helpers/instruction-entry.ts` exporting `putInstruction({ sessionID, key, value })`, `removeInstruction({ sessionID, key })`, `listInstructions({ sessionID })`, a key builder and the size guard.
- A single carrier switch `INSTRUCTION_INJECTION=native|synthetic`, with the synthetic prompt-plus-stash path retained as the fallback and logged with one warning per session.
- A second call site migrated the same way, one key per skill, for example `instr-task-skills-<skill>`.

### 2.3 Why the plugin cannot reach the API through its inputs

The plugin `Context` carries no client, no base URL and no credentials. `SessionDomain` is a `Pick` of `SessionApi` that omits `instructions`, and `context.rpc` reaches only host-registered definitions, so no RPC route carries the HTTP-only entry endpoints. The repository already solves this out of contract: `helpers/service-client.ts:244-256` constructs `@opencode/client` from a base URL and a Basic auth header resolved from the live registration file, and `helpers/instruction-entry-client.ts:21`, `:40`, `:48` calls the three entry methods against it. This migration adopts that transport; section 5.7 records what an upstream host would have to add to make it a contract.

### 2.4 What the ADR's own text gets wrong about this tree

Three statements in ADR-011 are stale against the working tree, and the plan follows the tree:

- The `<task_skills>` prepend is the block literal at `.opencode/plugins/helpers/workflow-subtask.ts:313`, not in the `116-157` range the ADR cites.
- ADR-010's `<workflow_instructions>` block already travels as an instruction entry, written by the `writeEntry` call at `.opencode/plugins/workflow.ts:141`, not as an `event.system` append. That call sends no `x-opencode-directory` header, because the site is out of this plan's scope, so the plan records its write status under the header rule as unverified (D5).
- The probe fixture `.opencode/plugins/tests/fixtures/instruction-entry-probe.ts` named in the ADR's validation record does not exist. Phase 4 recreates it as a module the live suite imports, because the loader scans root `.opencode/plugins/*.ts` only (`.opencode/instructions/opencode-plugin-interfaces.instructions.md:102`).

## 3. Scope and non-goals

In scope: the two instruction-injection call sites in this repository (the loader's steering blocks and the `<task_skills>` prepend), the carrier helper, the plugin-side dedupe that the native carrier replaces, the `INSTRUCTION_INJECTION` switch, the tests, the operator tool the rollback in section 8.4 runs (`scripts/instruction-entries.ts`), the audit record of the components that read user turns (R-69), and the operator-facing documentation of the one-turn deferral.

Not in scope: core runtime behavior, including `SessionInstructions.load` and its nested-`AGENTS.md` synthetic publication, which the ADR explicitly excludes; ADR-010's content, default source, no-truncation behavior and predicate, which this migration does not change; ADR-010's entry write at `.opencode/plugins/workflow.ts:141`, whose write carries no directory header, so its write status is recorded as unverified (D5); the Python-side systems; and any change to which guidance is selected or when.

In scope as a one-line exception: `.opencode/plugins/workflow.ts`. Phase 6 changes one line there, the `runWorkflow` call at `:291`, which passes the plugin context's `storage` handle into the workflow context through `RunWorkflowOptions.storage`. Nothing else in that file changes, and its entry write at `:141` keeps its current shape.

The `storage` handle is threaded through four production places and eight literals in seven test files. The four production places are the required `WorkflowContext.storage` member in `helpers/workflow-types.ts:121`, the required `RunWorkflowOptions.storage` member in `helpers/workflow-runner.ts:42-51`, the read in `createContext` at `helpers/workflow-runner.ts:402`, and the `runWorkflow` call at `.opencode/plugins/workflow.ts:291`. The eight literals are the `makeContext` helper in each of the five test files that build a `WorkflowContext` literal, and the option factories `options()` at `.opencode/plugins/tests/helpers/workflow-runner.test.ts:63`, `makeOptions()` at `.opencode/plugins/tests/helpers/workflow-runner-progress.test.ts:83-84` and `runnerOptions()` at `.opencode/plugins/tests/helpers/workflow-fork-fanout.test.ts:225`.

### 5.2 Hook and lifecycle flow

The loader registers one hook, `context.tool.hook('execute.before', ...)` (`.opencode/plugins/instructions-loader.ts:84`), and one `context` hook (`:124-129`) that exists only to serve the synthetic fallback until Phase 6.

1. `readFilePath(event.input)` yields the path; the touch is dropped when the path is missing or the tool is outside `TARGETED_TOOLS` (`:85-86`).
2. The agent resolves as `event.agent`, else `context.session.get({ sessionID }).agent`, else `'build'` (`:87-88`). This chain is unchanged.
3. `helper.resolveInstructions([filePath])` yields the matched instructions; the touch is dropped when the list is empty (`:90-91`).
4. `resolveInjectionCarrier(env, agent)` selects `native` or `synthetic` from the environment value alone and logs the selection. The selection table in section 5.6 is the authoritative rule: an explicitly set `INSTRUCTION_INJECTION` always wins over the default (D6), and the default flips once, in Phase 5, for every agent at once (D7). The loader passes `process.env` and the resolved agent name; `helpers/instruction-carrier.ts` emits the log line `carrier=<native|synthetic> agent=<agent>`. The staged agent class, `rug`, is the monitored cohort for the release window, not a routing branch: the agent name in that line is what tells the cohort's sessions apart from the rest. ADR-011 migration step 6's per-agent-class enablement is not implemented, because a process-wide environment value cannot select one agent class; the global default flip is the substitute and the section 8.3 removal gates are the compensating control (D7).
5. Native path: `publishInstructionSet({ sessionID, agent, directory, instructions, indexedPaths, storage })` in `helpers/instruction-carrier.ts` publishes one entry per matched instruction file and then sweeps stale keys. The loader passes `indexedPaths`, the union of the indexed instruction paths of every agent it has indexed and of the instruction files the glob scan found: it keeps one `InstructionContextHelper` per agent in its `helpers` map (`.opencode/plugins/instructions-loader.ts:61`, `:78`), and the union is the flattened `indexedPaths` and `allPaths` of every value in that map, never one helper's set, because `createIndex` drops the files whose `appliesToAgents` excludes the agent (`.opencode/plugins/helpers/instruction-indexer.ts:66-72`) and a sweep built from one agent's set would delete a live entry that belongs to another agent's scope (D9). The helper map holds only the agents this process has touched, so the unfiltered `allPaths` set is what keeps an entry whose source belongs to an agent this process has not indexed out of the sweep's delete set (D9). The loader passes its storage handle, so the carrier owns the per-session state. Each entry's value is one file's block, `buildSteeringMessage(formatInstruction(instruction, isReference))` from `helpers/instruction-payload.ts`, so a touch that matches N files publishes N `<steering>` wrappers where today it publishes one combined wrapper. The path set reaches the carrier through five hops: `createIndex` returns `indexedPaths: string[]` and `allPaths: string[]`, the loader's `indexerFactory` literal (`:73-76`) returns that index, `InstructionContextHelper` copies both from the resolved index inside `resolveInstructions` and exposes them, and the loader unions the per-helper sets and hands the union to the carrier as `indexedPaths`; the carrier turns it into entry keys and passes those to `sweepStaleEntries({ sessionID, directory, liveKeys })`.
6. Synthetic path: the existing token map, `context.session.prompt` (`:114`) and `context.storage.set(pendingKey(...), message)` (`:115`); the `context` hook pushes the stashed block onto `event.system` (`:127`). This path is untouched until Phase 6 removes it.
7. Failure policy. The handshake between the carrier and the loader has one shape, and it is stated here once. `helpers/instruction-entry-client.ts` raises the typed `InstructionCarrierUnavailableError`, whose `_tag` is `InstructionCarrierUnavailableError`, for every trigger in section 5.6. `helpers/instruction-carrier.ts` catches it: before any entry was written it logs the one warning per session and raises the typed `InstructionCarrierUnavailableError` to the loader; the loader catches that error and runs the synthetic path at `:93-121`, whose behaviour is unchanged: the synthetic publication is extracted from the hook body into a function that returns an `Effect` of `void`, and the carrier-unavailable arm of the loader's `Effect.catchTag` returns that effect, so the same `buildSteeringMessage` payload is delivered once, from Phase 2 until Phase 6 deletes the synthetic path (R-81, D18). The typed failure reaches that arm because the carrier's `Effect.tryPromise` catch mapper returns the typed error value instead of an effect, and the causes it throws reach the `Effect.catchDefect` arm as defects (section 6.2). The `Effect.orDie` at `:122` still wraps the whole hook, so a failed synthetic prompt write still fails the tool call. The task-skills publish and remove helpers reach the same per-session state through the storage handle the plugin context carries, which Phase 6 threads into the workflow context (section 6.6, D16). From Phase 6 the same failure keeps one shape: the carrier logs the one warning per session and raises the typed `InstructionCarrierUnavailableError`, and every call site handles that one error the same way. The carrier never handles its own failure. The loader's `Effect.catchTag` arm returns an empty effect instead of the synthetic publication, so no entry is written, no guidance is published for that turn and the tool call succeeds (D18); the task-skills site catches the same typed error at its own call site, logs nothing further and continues the child turn without the entry. A failure after at least one entry was written never reaches the loader: the carrier skips the remaining files, logs, and records each skipped file's entry key and rendered value in the session's carrier state, so the next touch republishes them without a body source the carrier does not hold, and no block is delivered by two carriers (R-77, D15). Every other failure, one that is neither carrier unavailable nor an oversize file, is logged by the loader and skips the guidance for that turn, with no fallback. The interception is Effect-native, because a plain try/catch around a yielded effect never fires: the typed error would stay a defect, escape into the `Effect.orDie` at `:122` and kill the tool call. Each failure kind has its own channel and its own combinator. `helpers/instruction-entry-client.ts` raises the typed `InstructionCarrierUnavailableError` as a thrown value. `helpers/instruction-carrier.ts` calls the entry client through `Effect.tryPromise({ try, catch })`, whose `catch` mapper keeps the raw cause, and the carrier's own routing branch sends that cause down one of two channels: the typed `InstructionCarrierUnavailableError` becomes a typed failure in the effect's error channel through `Effect.fail`, and every other cause becomes a defect through `Effect.die`. `Effect.promise` is not used for the entry call: it types its error channel as `never` and turns a rejection into a defect, so the typed carrier-unavailable failure would never reach the loader's `Effect.catchTag` and the fallback would never run. The loader's native branch ends in two combinators, in this order: `Effect.catchDefect` first, which handles the defect from the client call, logs it and skips the guidance for that turn, and `Effect.catchTag("InstructionCarrierUnavailableError", ...)` second, which handles the typed carrier-unavailable failure from the error channel and returns the synthetic publication effect. `Effect.catchDefect` recovers from defects only, so an interruption propagates instead of being logged as a skip, and `Effect.catchTag` recovers from typed failures only, so it never absorbs a defect. The order matters: the outer `Effect.catchTag` returns the synthetic effect, and a defect raised inside that effect, a failed prompt write, reaches the `Effect.orDie` at `:122` and fails the tool call exactly as today, while a failed native guidance write is logged and never kills the tool call.

### 5.3 Entry data model

| Element | Shape |
|---|---|
| Full-body key | `instr-<slug>` |
| Reference-only key | `instr-ref-<slug>` |
| List key form | the carrier normalizes the key form on read: `listEntries` and `findEntry` strip a leading `api/` from every returned key, so a list that answers `api/instr-<slug>` and a list that answers `instr-<slug>` both yield the bare key `instr-<slug>`. The bare form is canonical for the budget count, the sweep comparison and `instructionSlugFromKey`; the `api/` prefix is the runtime's source namespace and appears only in the rendered `<context key="api/instr-<slug>">`. The bare form is an assumption the Phase 1 unit case pins on both spellings and the Phase 4 live suite measures: the live suite records the form the server actually returns (D25). |
| Task-skills key | `instr-task-skills-<skill>` |
| Workflow key (untouched) | `workflow.instructions`, written by `.opencode/plugins/workflow.ts:141` with no directory header; that site's write status is unverified here (D5) |
| Slug | basename without `.instructions.md`, lowercased, every character outside `[a-z0-9]` mapped to `-`, repeats collapsed. Example: `.opencode/instructions/serena-gateway.instructions.md` gives `serena-gateway`. An instruction without a `path` takes its slug from the sanitised `description` instead, through `instructionSlugFor(instruction)` (D20). |
| Slug from key | strip `instr-ref-` first, then `instr-`; the remainder is the slug. `instr-ref-alpha` gives `alpha`, never `ref-alpha`. |
| Published set | keyed by slug, not by key, so a file that changes role has one entry: every publish deletes the counterpart key of the role it publishes, `instr-<slug>` when it publishes `instr-ref-<slug>` and `instr-ref-<slug>` when it publishes `instr-<slug>`, in the same touch. |
| Role change | two directions, both in the same touch as the publish: a file whose rendered body grows past the 256 KiB cap is published as a reference entry and its superseded full-body key is deleted, and a file published as a full entry has its superseded reference key deleted, which is how a file that held a reference entry and later fits the budget ends with one entry. The budget never downgrades a file that holds a full entry. |
| Value | one file's rendered steering block as a string: `buildSteeringMessage(formatInstruction(instruction, isReference))` (D2). The runtime renders a string verbatim inside `<context key="...">`. |
| Size limit | `Buffer.byteLength(JSON.stringify(value), "utf8")` at most 262144. |
| Budget rule | a file that already holds a full entry keeps that role and is not re-budgeted; the five-slot budget applies only to files without a full entry (D3). What counts as a full body, and which keys the count covers, is stated once, in section 5.5. |
| Skill name | the skill directory name inside `instr-task-skills-<skill>`. It is used as it stands when it already matches `^[a-z0-9][a-z0-9._-]*$`; otherwise it is lowercased, every character outside `[a-z0-9._-]` is mapped to `-`, and a leading character outside `[a-z0-9]` is replaced by `0`. |
| Sweep source | the union of the indexed instruction paths of every agent the loader has indexed, taken from `createIndex`'s agent-filtered `indexedPaths: string[]` (`.opencode/plugins/helpers/instruction-indexer.ts:66-72`), carried by `InstructionContextHelper.indexedPaths`, unioned by the loader over every helper it holds and passed to `publishInstructionSet` as `indexedPaths`, not the files matched by the current touch. The union is what keeps an entry that belongs to another agent's scope: a file whose `appliesToAgents` excludes the current agent is absent from that agent's index, so a sweep built from one agent's set would delete a live entry (D9). A sweep built from the current touch would delete valid entries for files it simply did not match. The carrier turns that path set into entry keys with `instructionEntryKey({ path })` and `instructionReferenceKey({ path })`, adds the keys the current touch published, including the key of an instruction without a path, and hands the result to `sweepStaleEntries({ sessionID, directory, liveKeys })`, where `liveKeys: string[]` is the set of live entry keys (D9, D20). Scope: the sweep deletes only the loader's own key families in the current session, `instr-` and `instr-ref-`, and only a key whose source file is gone. The live-key set covers the agents this process has indexed and every instruction file the glob scan found, so an entry whose source file still exists survives even when the agent that owns that file was never indexed in this process; the loader's helper map holds only the agents touched in this process and the index is filtered per agent, so the unfiltered set is what preserves those entries. |

The key families are disjoint: `instr-`, `instr-ref-` and `instr-task-skills-` never collide with `workflow.instructions`, and no two files in the single glob directory share a basename. The loader's own families are `instr-` and `instr-ref-`. The stale-key sweep covers those two families and leaves `instr-task-skills-` alone, because the task-skills site owns that family and no instruction file stands behind it; the full-body budget counts the keys section 5.5 defines. The index is cached per agent for the plugin lifetime (`.opencode/plugins/instructions-loader.ts:61`, `:78`), so the indexed path set is the file system as of the first touch per agent per process: the sweep reflects that set and does not observe a file deleted later in the same process (D9).

### 5.4 Session scoping

| Call site | Session the entries belong to |
|---|---|
| Loader steering blocks | the touched session, `event.sessionID` |
| Task-skills prepend | the child subtask session returned by `resolveSessionID` (`.opencode/plugins/helpers/workflow-subtask.ts:922`) |

The two sites share one warning latch only when they address the same session. The loader latches under the touched session, `event.sessionID`, and the task-skills site latches under the child session `resolveSessionID` returns; those are the same session when the loader's `execute.before` hook fires for a tool call inside the child subtask session, and different sessions otherwise. The storage handle and the key shape are shared either way, so a transport outage logs one warning per affected session: one in the child session when the two sites address it, and one in each session when they do not (D16).

The server keys entries by `(session_id, key)`, so the plugin holds no cross-session entry state. The plugin-side session state is the synthetic token map, which dies with the synthetic branch in Phase 6, and the carrier's per-session key `instruction-carrier/<sessionID>`, which holds `{ warned, unpublished }`: `warned` records that the transport-failure warning was already logged for that session, and `unpublished` lists every file a failed publication skipped as its entry key and its rendered value, key plus value, so the carrier can republish them at the start of the next touch without a body source it does not hold. The carrier module owns that key. It survives Phase 6, because the failure policy outlives the synthetic branch (D3, D15, D16).

### 5.5 Idempotency and the body budget

Dedupe on the native path is server-side: `writeEntry` is the put-if-changed write. It reads the stored value with list-and-filter (`.opencode/plugins/helpers/instruction-entry-client.ts:25-28`), asks the pure decision function `isEntryValueCurrent` whether the stored value matches the new one, skips the write when it does and otherwise upserts, and reports the outcome as an `EntryResult` whose `status` is `written`, `unchanged` or `failed`, not as a boolean. `removeEntry` reports `removed`, `absent` or `failed`. `.opencode/plugins/workflow.ts:18` imports both, and that site is out of scope. The server upserts on `(session_id, key)`, so a re-published identical value produces no change event.

The full-versus-reference budget stays at five full bodies per session, and the carrier counts against `FULL_BODY_BUDGET = 5` in `helpers/instruction-carrier.ts`. The count comes from the session's own entry list, so the plugin keeps no counter of its own. One key counts as one full body when its normalized bare form starts with `instr-` and does not start with `instr-ref-` or `instr-task-skills-`: a reference entry never consumes a slot, a task-skills entry never consumes a slot, and `workflow.instructions` is not the loader's key and never consumes a slot. Files beyond the budget are published as reference entries. A file that already holds a full entry keeps that role: the five-slot budget applies only to files without a full entry, so a re-touched file is never downgraded to a reference (D3).

A file whose rendered body exceeds the 256 KiB cap is published as a reference entry with a loud log; it is never truncated (D3). That cap is the one trigger that downgrades a file that already holds a full entry: the superseded full-body key is deleted in the same touch. The role change runs in both directions: a file published as a full entry has its superseded reference key deleted in the same touch, so a file that held a reference entry and later fits the budget ends with one entry, and a file never holds both keys.

### 5.6 Transport, carrier selection and fallback

`helpers/service-client.ts` is the only module that resolves a base URL, a password or an auth header. It gains a trailing optional directory argument, and an entry request that carries a directory sends `x-opencode-directory` (D5). Both call sites in this plan always carry one: the loader's carrier sends `context.location.directory`, and the task-skills site sends the working directory the child session inherits, which the site holds as `context.directory` (`.opencode/plugins/helpers/workflow-subtask.ts:942`). ADR-010's site at `.opencode/plugins/workflow.ts:141` keeps its current call shape, sends no header, and its write status is recorded as unverified (D5). The operator tool carries one too: its `--directory` option defaults to the repository root, and the tool passes that directory into every call it makes, so the rollback's list and delete requests stay inside the directory scope (D27). The credentials never appear outside that module (R-72).

Carrier selection is one function, `resolveInjectionCarrier(env, agent)`, with two inputs: the environment value `INSTRUCTION_INJECTION` and the resolved agent name. The environment value alone selects the carrier; the agent name is carried only for the log line, so the `rug` cohort's sessions can be told apart from the rest (D7). Phase 6 deletes the function and the flag together, and the native carrier becomes the only carrier:

| `INSTRUCTION_INJECTION` | Result |
|---|---|
| `synthetic` | the synthetic path, whatever the agent class is |
| `native` | the native path |
| unset | the synthetic path through Phase 4, the native path from Phase 5 (D7) |
| any other value | the default carrier, with one warning that names the rejected value. The warning is latched per distinct rejected value in a module-level set in `helpers/instruction-carrier.ts`, so each rejected value is named once per process and a second, different rejected value is named as well; the per-session guard covers the transport-failure warning only |

That table holds the whole selection rule. The default flips once, in Phase 5, for every agent at the same time, and no later phase changes it. The staged agent class, `rug`, is the monitored cohort for the release window, not a routing branch: the carrier-selection log line records the agent name, so the cohort's sessions can be told apart from the rest (D7).

Fallback triggers are a missing client method, an HTTP 401, 403 or a decoded 404 on an entry route, any status an entry route does not declare, and an unresolvable server address or credentials. The entry client owns the detection: it checks that `client.session.instructions.entry` exists before it calls it, so a client without the method raises the typed `InstructionCarrierUnavailableError` instead of a `TypeError`, and it catches a failed entry call and maps it to a typed error. The mapping from each concrete error to its outcome is:

| Source | Concrete error | Outcome |
|---|---|---|
| the client method is missing | the absence of `client.session.instructions.entry`, detected before the call | carrier unavailable, the typed `InstructionCarrierUnavailableError` |
| the transport cannot be resolved | `getClient()` throws, no candidate server answers | carrier unavailable, the typed `InstructionCarrierUnavailableError` |
| HTTP 401 | `isUnauthorizedError` | carrier unavailable, the typed `InstructionCarrierUnavailableError` |
| HTTP 403 | `isForbiddenError` | carrier unavailable, the typed `InstructionCarrierUnavailableError` |
| HTTP 404, decoded by the client | `isSessionNotFoundError` | carrier unavailable, the typed `InstructionCarrierUnavailableError` |
| a status the entry route does not declare, a 404, a 405 or a 413 the client leaves undecoded | the thrown `ClientError` with `reason: "UnexpectedStatus"` | carrier unavailable, the typed `InstructionCarrierUnavailableError` |
| an error the client cannot classify | a `ClientError` whose `reason` is another value, such as `Transport` or `MalformedResponse`, or any other thrown value | not carrier unavailable: logged, the guidance for that turn skipped, no fallback |
| a value over 256 KiB, caught by the local guard | the typed oversize error, `_tag: "InstructionEntryValueTooLargeError"`, `actualBytes`, `maxBytes`, `message` | oversize file: logged and published as a reference entry, no fallback |
| HTTP 413, decoded by the client into the typed oversize error | `isInstructionEntryValueTooLargeError` | oversize file: logged and published as a reference entry, no fallback, the same outcome as the local guard |
| anything else | the error, unchanged | not carrier unavailable: logged, the guidance for that turn skipped, no fallback |

Every carrier-unavailable outcome above is one typed error, `InstructionCarrierUnavailableError`, with `_tag: "InstructionCarrierUnavailableError"`, raised by `helpers/instruction-entry-client.ts`; the carrier matches on that tag, returns it from the `catch` mapper of `Effect.tryPromise`, so the effect's error channel carries that typed failure, and the loader catches it with `Effect.catchTag("InstructionCarrierUnavailableError", ...)` (section 5.2 step 7). The four guards the table names are declared in the promise surface the carrier imports, `isUnauthorizedError`, `isSessionNotFoundError`, `isInstructionEntryValueTooLargeError` and `isForbiddenError` (`.opencode/node_modules/@opencode/client/dist/promise/generated/types.d.ts:3370`, `:3401`, `:3451`, `:3544`). The oversize error is matched on its tag as well: `isInstructionEntryValueTooLargeError` matches the local guard's error, because the local guard raises the same field set the SDK type carries, and it matches a server 413 only when the client decodes that status into the typed error. The typed guards are checked before the `reason` rule, so the two outcomes stay disjoint: a decoded 413 is an oversize file, and an undecoded 413 is an `UnexpectedStatus`, which is carrier unavailable. The installed client declares 413 among the entry PUT route's statuses (`.opencode/node_modules/@opencode/client/dist/chunks/pty-handoff-qzsnm4q8.js:501`), and the Phase 4 live arm records which of the two branches the client takes (D26, Q5). The local guard rejects any value above 262144 bytes before the request, so the oversize outcome never depends on that branch.

The client exports no guard for a route-not-found 404 or a 405: a decoded session 404 arrives as `SessionNotFoundError` through `isSessionNotFoundError` and is carrier unavailable, and a 404 or a 405 the client leaves undecoded arrives as the thrown `ClientError` with `reason: "UnexpectedStatus"`, which the table above also maps to carrier unavailable (D26). The instance carries only `reason` and `name`: `detail` appears in the constructor options type (`.opencode/node_modules/@opencode/client/dist/promise/generated/client-error.d.ts`) and never reaches the instance, because the implementation reads `options.detail` to build the message and assigns `this.reason` alone (`.opencode/node_modules/@opencode/client/dist/chunks/pty-handoff-js54wxgp.js:2-10`). The carrier therefore classifies on `reason` alone and reads no status: it never parses the message and never reads `cause`, which the client types as `unknown` and fills with `{ status }` (`.opencode/node_modules/@opencode/client/dist/chunks/pty-handoff-qzsnm4q8.js:56`). A `ClientError` with any other `reason` is unclassifiable and takes the catch-all row of the table above. The local size guard raises the same typed oversize error, so the carrier's oversize branch is reachable without a server round trip. No module outside `helpers/instruction-entry-client.ts` reads a raw thrown value. The carrier matches on the typed `InstructionCarrierUnavailableError` and raises it to the loader, which runs the synthetic fallback; that handshake is stated once, in section 5.2 step 7. Each trigger logs exactly one warning per session and, until Phase 6, one synthetic delivery of the same `buildSteeringMessage` payload. From Phase 6 the synthetic path is gone, so the same failure logs the one warning per session and skips the guidance for that turn (D18). ### 5.8 Phase outline

The six phases below are the only phases. Section 6 has one table per phase, with the same files.

1. **Phase 1, carrier foundation.** Build the carrier primitives: the entry-client exports, the key builders, the size guard, the directory-scoped transport, the pinned client, the payload module that owns `formatInstruction` and `buildSteeringMessage` (D19), and the operator tool `scripts/instruction-entries.ts` that the rollback in section 8.4 runs.
2. **Phase 2, native publication path.** Add the flag-gated native path to the loader: the loader reads `INSTRUCTION_INJECTION` from `process.env` on every touch and resolves the carrier with `resolveInjectionCarrier(process.env, agent)`, and the new carrier module holds the per-file loop, the sweep and the transport-failure fallback. The native branch returns before the token map, so it reads no token and writes none. The synthetic path stays the default and stays intact.
3. **Phase 3, retire the dead `idempotencyKey` field.** Delete the dead field from the type and its assignment in the helper, and update the helper's test. The token map itself stays with the synthetic branch and goes in Phase 6 (D22).
4. **Phase 4, test suites.** Add the unit cases, the live integration cases, the probe fixture, the no-user-turn regression case and the audit record of the components that read user turns (R-69).
5. **Phase 5, rollout and default flip.** Record the live measurements and the dual-run comparison, flip the default to `native` for every agent in one step, and mark the `rug` agent class as the monitored cohort for the release window. Phase 5 also owns the release-window entry list: the live suite reads it when the default flips and again when the window closes, so the third removal condition can close before Phase 6 starts. The flag precedence ships in Phase 2 with the function that carries it, so Phase 5 changes the default alone.
6. **Phase 6, second call site and synthetic retirement.** Migrate the `<task_skills>` site, then delete the synthetic branch, the flag, the token map and the `context` hook together. Phase 6 starts only after the three removal gates in section 8.3 close, which leaves one release at the native default before the synthetic branch goes.

No phase consumes a file, export or behavior that a later phase introduces. The switch to the native carrier happens in Phase 2, before any mechanism the synthetic path depends on is removed in Phase 6. Phase 5 and Phase 6 are separated by the release window that section 8.3 requires; no phase sits between them. The window-close reading of the release-window entry list is a Phase 5 step executed inside that window, so the third removal condition closes on evidence Phase 5 produced, not on a Phase 6 artifact.

### 7.4 The live suite

The live suite is the only acceptable evidence for the carrier, because mocked shapes passed while the live runtime rejected them (R-70). The default test run collects the file, because vitest's default include pattern matches `*.test.ts` and `.opencode/vitest.config.ts:26` excludes only `**/node_modules/**` and `**/.stryker-tmp/**`; the suite keeps itself out of the default gate with a suite-level skip guard, so every case is skipped unless `E2E_PROBE_ENABLED=1` and the module opens no connection at import time, and the suite runs only through `E2E_PROBE_ENABLED=1 just opencode::test -- plugins/tests/instruction-entry-client.live.test.ts`. It needs a running opencode server that `helpers/service-client.ts` can reach, either the background service the plugin host already runs, whose registration file the resolver parses, or a private one started with `opencode serve` in the working directory under test, and a configured model provider for the reply arms. When a prerequisite is absent the suite skips the live arms and reports which one is missing instead of failing on a raw connection error or a 401, and a skipped run satisfies no gate: the Phase 5 default flip and the section 8.3 removal conditions wait for a green run against a live server, and neither gate fails the build on a missing prerequisite. It runs against a live server with `E2E_PROBE_ENABLED=1` and covers six things: the treatment arm (the token in the written entry appears in the next assistant reply), the control arm (a denied write leaves the token absent), the durability arm (the key is listed and the delete removes it), the server size arm (the typed client, called past the local guard, is refused with the server's 413, and the suite records whether the installed client decodes it into the oversize error or leaves it an `UnexpectedStatus`), the carrier size arm (the local guard rejects before any request, so the carrier publishes the file as `instr-ref-<slug>` with the loud log and no truncation), the key form the server answers with, the bare `instr-<slug>` or the `api/`-prefixed form (D25), and the measurements Phase 5 records.

The observation channel is the model's reply, as in ADR-011's own validation: the suite creates its own session in the working directory the live server serves, writes a fresh random token as the entry value, prompts that session id with tools disabled, and reads the assistant's reply from the session's messages through the `@opencode-ai/sdk` route `client.session.messages` (`.opencode/node_modules/@opencode-ai/sdk/dist/gen/sdk.gen.d.ts:168-170`), on the client `getSdkClient(directory)` returns; the entry calls go through `getClient(directory)` with the same working directory, so every entry request carries `x-opencode-directory` (D5); the session read goes through `getSdkClient(directory)`, whose GET requests carry the directory as a `?directory=` query parameter, because the SDK client moves the header into the query string and deletes it on GET and HEAD requests (`.opencode/node_modules/@opencode-ai/sdk/dist/client.js:18-30`). The session comes from `client.session.create({ body: { title }, query: { directory } })` on that client, and the suite reads the session id from the response. Both clients come from `helpers/service-client.ts`, the repository's only credential resolver, so the suite holds no URL, password or auth header of its own. The command that reads it is `E2E_PROBE_ENABLED=1 just opencode::test -- plugins/tests/instruction-entry-client.live.test.ts` (`.opencode/justfile:14`). The dual run that gates the default flip is two invocations of that command, `INSTRUCTION_INJECTION=native ...` and `INSTRUCTION_INJECTION=synthetic ...`, because one invocation carries one flag value; each arm runs in its own fresh session, each arm writes its own marker, and the record file holds one row per arm stating whether that arm's marker appeared in the reply, with a reply that followed both markers recorded as followed by both rather than as a failed comparison. Removals are observed through the session's entry list, because the runtime owns the narration text (R-36). The same command produces the release-window entry list: the suite reads the session's entry list when the default flips and again when the window closes, and both readings land in `docs/plan/2026-10-20-adr-011-instruction-entries/release-window-entries.md`. The evidence gates the default flip in Phase 5 and the removal gates in section 8.3: neither closes without the treatment and control arms recorded. A skipped run records nothing and closes neither gate, so the Phase 5 default flip and the section 8.3 removal conditions wait for a green run against a live server.

### 8.4 Rollback

The procedure works against the state the migration leaves behind. It does not depend on a pre-migration form of any file.

1. Set `INSTRUCTION_INJECTION=synthetic` in the opencode server's environment and restart that server, or the service that hosts it. The loader reads the value from the host process environment (`process.env`), and a running process keeps the environment it started with, so exporting the variable in an operator's shell changes nothing until the host process restarts. After the restart an explicit value outranks the default (D6), so every new session returns to the synthetic publication path, the staged cohort included. No code change and no harness redeploy; the host process is restarted. Sessions that were already open when the restart happened keep the native carrier until they end, and their entries are cleared by step 2's deletion loop. Capture the restart timestamp and the sessions the server holds: `opencode session list` prints the project's top-level sessions, newest first, and the operator keeps that output next to the timestamp, so the sessions that were open at the restart and still need step 2's deletion loop are known.
2. Delete the entries the native path wrote, so the reverted site stops rendering guidance from them. The prefix names one family per invocation, so the rollback runs three commands for every session captured in step 1, each with the working directory that session was created in, the repository root for this project's sessions: `just scripts::instruction-entries delete --session <sessionID> --prefix instr- --directory <path>`, then the same command with `--prefix instr-ref-` and then with `--prefix instr-task-skills-`. The script imports `.opencode/plugins/helpers/instruction-entry-client.ts` by relative path, through bun, and calls `removeEntry({ sessionID, key, directory })` for each matching key the session's entry list holds, which issues `DELETE /api/experimental/session/:sessionID/instructions/entries/:key` with the `x-opencode-directory` header the directory argument carries (D5, D27). `--prefix instr-` clears the loader's full-body family `instr-<slug>` and touches neither the reference family nor the task-skills family; the reference family is cleared by `--prefix instr-ref-` and the task-skills family by `--prefix instr-task-skills-`, because the sweep and the budget treat those two families separately (section 5.3, section 5.5), and a prefix must not reach a family it does not name. The task-skills entries render exactly like the loader's, so the rollback clears them too, one family per invocation. The tool matches on the bare key form the read side normalizes (D25), so a key the server answers as `api/instr-<slug>` matches. The tool accepts only a key in the `instr-` namespace and one of the three family prefixes, so it cannot delete ADR-010's `workflow.instructions` entry. It prints one `deleted <sessionID> <key>` line per key and a final `removed <n> entries` line, and exits 0 only when every delete succeeded, so a partial cleanup shows a non-zero exit. To see what a session holds before deleting anything, run `just scripts::instruction-entries list --session <sessionID> --directory <path>`, which prints the session's entry keys, one per line.
3. Verify the rollback with the cases that exist in the current tree: the synthetic-path cases in `.opencode/plugins/tests/instructions-loader.test.ts` and the removal cases in `.opencode/plugins/tests/helpers/instruction-carrier.test.ts` pass with the carrier pinned to `INSTRUCTION_INJECTION=synthetic`, which the six legacy cases set on `process.env` for the duration of the case (section 6.2), and `just opencode::test -- plugins/tests/instructions-loader.test.ts` (`.opencode/justfile:14`) is green. Those synthetic-path cases stay in the tree from Phase 2, because the synthetic carrier is the default until Phase 5 and the transport-failure fallback until Phase 6.

After Phase 6 the flag and the synthetic branch are gone, so the rollback for that state is a redeploy of the previous release. Entries are additive and change no schema, so a redeployed site resumes its previous publication path, and step 2 still clears the leftovers.

### 10.2 Migration acceptance criteria

1. From Phase 5 the native carrier is the default for the loader's steering blocks for every agent, and from Phase 6 it is the only carrier: after Phase 6 no instruction text reaches `context.session.prompt` from `.opencode/plugins/instructions-loader.ts`. The retained `<task_skills>` prepend in `.opencode/plugins/helpers/workflow-subtask.ts:313` is the accepted exception, listed in section 8.2.
2. Selection is unchanged: the same 18 files match `.opencode/instructions/*.instructions.md`, and the `createIndex` call is verbatim.
3. The gate is unchanged: `TARGETED_TOOLS` applied after `readFilePath(event.input)`.
4. The payload is unchanged per file: each entry value equals `buildSteeringMessage(formatInstruction(instruction, isReference))` byte for byte, so the `<steering>` wrapper and the `<instruction>` rendering are unchanged and one combined block becomes one block per file (D17, D19).
5. Every entry request the loader's carrier issues sends `x-opencode-directory` with `context.location.directory`, the task-skills site sends the working directory it holds for the child session, and the live suite's own entry requests carry the same header with the working directory its live session is created in, while its session read carries the same directory as a `?directory=` query parameter, because the SDK client deletes the header on GET requests (D5). ADR-010's site is out of scope, sends no header, and its write status is recorded as unverified (D5). The operator tool's own requests carry the header with the directory its `--directory` option holds, which defaults to the repository root (D27).
6. Every entry value is measured with `Buffer.byteLength(JSON.stringify(value), "utf8")`; a value above 262144 bytes is not sent, and the file is published as a reference entry with a loud log. Nothing is truncated (D3).
7. Every key matches `^[a-z0-9][a-z0-9._-]*$`, and the families `instr-`, `instr-ref-`, `instr-task-skills-` and `workflow.instructions` never collide.
8. Exactly one carrier serves a given loader block in a given session; the entry path and the synthetic path never both run for one block. The `<task_skills>` site in section 8.2 is the one exception, and it keeps its prepend beside its entry (D4).
9. After Phase 6, `instruction_load:*`, `idempotency/<sessionID>`, `pending/<sessionID>`, `ResolvedInstruction.idempotencyKey`, `FULL_SLOT_BUDGET` and `INSTRUCTION_INJECTION` do not appear in any production source file under `.opencode/plugins/`, where production means `.opencode/plugins/**` with `.opencode/plugins/tests/**` excluded; a test file may name a retired string in a case that asserts its absence. The carrier's `instruction-carrier/<sessionID>` key is the one exception, because the failure policy outlives the synthetic branch (D16), and the carrier keeps the limit under its own name, `FULL_BODY_BUDGET` (section 5.5). The Phase 6 exit criteria and the S5 exit signal grep the same list.
10. A transport failure on the native path logs exactly one warning per session and never fails the tool call. The carrier's `Effect.tryPromise` catch mapper returns the typed `InstructionCarrierUnavailableError`, so the native branch's failure channel carries that typed failure in both periods and the handshake keeps one shape, and every other cause is thrown by the mapper and reaches the loader as a defect. Until Phase 6 the loader's `Effect.catchTag("InstructionCarrierUnavailableError", ...)` catches it and the synthetic path carries the guidance; every other failure is recovered with `Effect.catchDefect`, which excludes interruption, so an interrupted tool call is not turned into a logged skip; from Phase 6 the same arm returns an empty effect, so the warning is still logged, the guidance for that turn is skipped and the tool call succeeds, because the synthetic branch no longer exists (D18); the task-skills site catches the same typed error at its own call site and continues the child turn without the entry. The synthetic path's own prompt write keeps today's behaviour under `Effect.orDie`, so a failed prompt write still fails the tool call.
11. The live suite passes against a live server and reads the model's reply through the channel named in section 7.4; the suite needs a reachable opencode server, the background service or one started with `opencode serve` in the working directory under test, and a configured model provider; when a prerequisite is absent it skips the live arms and reports which one is missing, and a skipped run satisfies no gate; the probe fixture runs inside that suite, because the suite is its only runner; mocked suites alone are not accepted as evidence.
12. The dual-run comparison record exists before the synthetic branch is deleted, and the end-of-window entry list is recorded in `docs/plan/2026-10-20-adr-011-instruction-entries/release-window-entries.md` before the third removal condition closes, so the synthetic branch is never deleted before the evidence that condition asks for exists.
13. The `<task_skills>` site publishes an entry for the child session through the carrier's task-skills helpers, keeps a removal path, and keeps the prepend for the life of the migration, listed in section 8.2 (D4, D21).
14. Every decision row in section 9.3 states what it resolves, the phase that implements it, and the ADR-011 amendment it needs, and every decision referenced anywhere in this plan exists in that table.
15. Every open question in section 9.2 names a phase that defines the resolving activity, or is labeled carried forward with the condition for resolving it.
16. The repository's own gates pass: `just .opencode/deps` (the frozen install), `just opencode::test`, `just opencode::lint`, `just opencode::typecheck`, `just opencode::mutation` (`.opencode/justfile`), and `just ci` at the root (`justfile`). The mutation gate follows the rule the section 6 preamble states: it runs in full from Phase 6, and every phase before it passes `SKIP_MUTATION=1 just ci`, because the carrier's branches are only complete after Phase 6's cases (`scripts/ci.sh:83`, `:84`).
17. The stale-key sweep compares the session's entries with the entry keys derived from the union of the indexed instruction paths of every agent the loader has indexed and the unfiltered instruction-file set the indexer's scan found, and the path set reaches the carrier through `createIndex` → the loader's `indexerFactory` literal → `InstructionContextHelper.indexedPaths` and `InstructionContextHelper.allPaths`, which the helper copies from the resolved index inside `resolveInstructions` → the union over the loader's `helpers` map, one set per agent → `publishInstructionSet({ indexedPaths })` → `sweepStaleEntries({ liveKeys })`, so the sweep never sees an empty live-key set, never sees one agent's set alone, and never deletes an entry whose source file still exists, including an entry whose source belongs to an agent this process has not indexed (D9).
18. Before Phase 6: an `INSTRUCTION_INJECTION` value other than `native` or `synthetic` selects the default carrier and logs one warning naming the rejected value; the warning is latched per distinct rejected value, so each rejected value is named once per process and a second, different rejected value is named as well. After Phase 6 the flag and `resolveInjectionCarrier` are gone, so no value is rejected and no such warning is logged.
19. A file that already holds a full entry keeps that role when the five-slot budget is exhausted, and an oversize file is published as a reference entry with no fallback to the synthetic path; the 256 KiB cap is the one trigger that downgrades a file that already holds a full entry.
20. Before Phase 6: the loader selects the carrier with `resolveInjectionCarrier(process.env, agent)`: the environment value alone selects the carrier, the agent name is carried only for the log line, and the line the carrier module emits reads `carrier=<native|synthetic> agent=<agent>`. No per-agent-class enablement exists, because a process-wide environment value cannot select one agent class; the global flip and the section 8.3 gates are the compensating control (D7). After Phase 6 the loader calls `publishInstructionSet` directly, no carrier is selected and no carrier-selection log line is emitted (section 5.1).
21. The entry list's key form is normalized on read: a list that answers `api/instr-<slug>` and one that answers `instr-<slug>` both yield the bare key, the bare form is what the budget count, the sweep comparison and `instructionSlugFromKey` use, and the live suite records the form the server actually returns (D25).
22. The carrier-unavailable classification reads only what the installed client puts on the error instance: the four typed guards and `ClientError.reason`. A status the route does not declare is carrier unavailable through `reason: "UnexpectedStatus"`; every other error is not carrier unavailable, and it is logged, the guidance for that turn is skipped and no fallback runs (D26).
23. The task-skills publish and remove helpers take the storage handle they need in their signature, `publishTaskSkills({ sessionID, directory, skills, storage })` and `removeTaskSkills({ sessionID, directory, key, storage })`, and Phase 6 threads the plugin context's storage into the workflow context through the required `RunWorkflowOptions.storage`, which `createContext` reads into the required `WorkflowContext.storage`, so both carrier entry points reach the same per-session state through the same handle; the latch is per session, so a transport outage logs one warning per affected session, and one warning in the child session when the loader's hook fires inside it (D16, section 5.4).
24. The operator tool `scripts/instruction-entries.ts` carries its own contract: every command takes `--directory <path>`, which defaults to the repository root, and the tool passes that directory into every call it makes, so its list and delete requests carry `x-opencode-directory` (D5, D27); `--dry-run` performs the session's list request, prints the keys the delete would touch and suppresses the DELETE requests, so the listing is itself a request and only the deletions are suppressed; `--prefix` names exactly one family per invocation, `--prefix instr-` covering the loader's full-body family `instr-<slug>` and matching neither the reference family `instr-ref-<slug>` nor the task-skills family `instr-task-skills-<skill>`, with `--prefix instr-ref-` and `--prefix instr-task-skills-` naming the other two, and `--key` accepting only a key in the `instr-` namespace, so the tool cannot delete ADR-010's `workflow.instructions` entry; and the tool's case file drives it through the `run(argv, deps)` seam with stubs, because the transport resolver builds the client itself and offers no place to hand a stub client, so no live server and no module mock is needed (D27).
